# Control-flow structuring and pattern matching: how decompilers lift graphs, and what fits mentalc

Scope: how decompilers turn a control-flow graph into higher-level constructs by matching region patterns (interval analysis, structural analysis, Cifuentes, Phoenix, Dream, rev.ng, SAILR, Ghidra, Hex-Rays, Binary Ninja), what they do when no pattern matches or several do, and the pattern-matching machinery behind them (graph rewriting and graph grammars, critical pair analysis, tree-pattern matching and BURS, approximate graph matching). Each part ends with what it says for mentalc's level lifting, where an upper-level step (move, activation, goal, outcome) would be recognized as a pattern over the lower-level graph of effect nodes, and a near-miss of a pattern could be a finding.

| System or idea | One line |
|---|---|
| Interval analysis (Allen 1970, Cocke 1970) | Splits a CFG into single-entry intervals and repeats on the graph of intervals; reducible graphs collapse to one node. Built to speed up data-flow analysis. |
| Structural analysis (Sharir 1980; Muchnick 1997) | Matches a fixed set of region schemas (block, if-then, if-then-else, switch, while, self-loop, natural loop) in post-order and collapses each match; leftovers become "proper" (acyclic) or "improper" (cyclic) regions. |
| Cifuentes, dcc (thesis 1994) | First decompiler structurer: interval-based loops, post-dominator-based conditionals, four short-circuit patterns for compound conditions. |
| Phoenix (Schwartz et al., USENIX Security 2013) | Structural analysis made semantics-preserving (schemas match shape and predicates) plus iterative refinement: when stuck, turn one carefully chosen edge into a goto and try again. |
| Dream (Yakdan et al., NDSS 2015) | Pattern-independent: computes the boolean reaching condition of every node in a region, starts from `if (cond) {node}` per node and refines into if/else, switch and loops; zero gotos. |
| Dream++ (Yakdan et al., IEEE S&P 2016) | Dream plus readability transformations, validated by a user study with malware analysts. |
| rev.ng "Combing" (Gussoni et al., AsiaCCS 2020) | Goto-free: enforces graph properties (single entry, single successor, diamond shape) by duplicating nodes until every conditional dominates everything up to its post-dominator. |
| SAILR (Basque et al., USENIX Security 2024) | Compiler-aware: finds the GCC optimization behind each goto and inverts it (merge duplicated blocks, re-duplicate condensed blocks); keeps the gotos the programmer wrote. Measures closeness to source by graph edit distance. |
| Ghidra (NSA, open source) | Pattern-matching rule set applied in fixed order until nothing fires; when stuck, a trace heuristic picks the "likely goto" edge. |
| Hex-Rays (commercial) | Pattern matching with gotos and some code duplication (return statements); closed source. |
| Binary Ninja (commercial, 2024 structurer) | Pattern-independent over single-entry single-successor regions, mixing rev.ng and Dream ideas with gotos as a last option. |
| SoK "No Goto, No Cry?" (Behner et al., IEEE S&P 2025) | Every structurer must answer four questions: which subgraphs are resolvable, what to do with the rest, in what order, and at what cost. |
| Graph rewriting (DPO/SPO; AGG, GROOVE, GrGen, PROGRES) | Rules `L → R` applied at a match of `L`; negative application conditions forbid a context; critical pair analysis lists every pair of rules that can disable each other. |
| BURS and iburg (Pelegrí-Llopart and Graham 1988; Fraser, Hanson, Proebsting 1992) | Tree-pattern instruction selection: overlapping rule matches resolved by dynamic programming to the minimum-cost cover. |
| Rule-library synthesis (Buchwald, Fried, Hack, CGO 2018) | Synthesizes every minimal IR pattern for each machine instruction; finds tens of thousands of rules missing from GCC and Clang. |
| LISC (Hasabnis and Sekar, ASPLOS 2016) | Lifting run in reverse from the compiler: learns assembly-to-IR translation from GCC's code generator. |
| Graph edit distance; error-tolerant matching (Bunke, Messmer) | The cost of the cheapest edit script between two graphs; NP-hard, used for near-matches in pattern recognition and as SAILR's metric. |
| "Bugs as deviant behavior" (Engler et al., SOSP 2001) | Infers what code believes from what it usually does and reports the deviations, ranked statistically. |

## Interval analysis, Sharir, Cifuentes and structural analysis: the schemas and the reduction loop

### Takeaway

Classical structuring is a reduction loop. Visit nodes in post-order (inner before outer), match the region at the node against a fixed library of schemas, collapse the match into one node labelled with the schema, and repeat until one node is left. What no schema matches becomes a proper or improper region, and is emitted with gotos. The method was built for data-flow analysis, where only reachability matters, and it carries that blind spot into decompilation.

### Cited Findings

- Interval analysis and structural analysis were built for optimizing compilers. Interval analysis "deconstructs the CFG into nested regions called intervals" whose nesting speeds up data-flow analysis. Structural analysis is "a refined form of interval analysis" built so that syntax-directed data-flow analysis for ASTs could run on low-level code. Decompilers adopted both later. [V] — [Dream, NDSS 2015, §VIII](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Structural analysis "matches a set of region schemas over the CFG by repeatedly visiting its nodes in post-order. … When a match is found, all nodes matched by the schema are collapsed or reduced into a single node that represents the schema matched." Example: three nodes match an if-then-else and collapse, and the result then matches a do-while, giving `do { if (c1) … else … } while (c2)`. [V] — [Phoenix, USENIX Security 2013, §2.1](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- When nothing more matches, structural analysis reduces acyclic and cyclic leftovers into proper and improper regions; "both of these regions indicate that no high-level structure can be identified in that subgraph and thus goto statements will be emitted". [V] — [Phoenix §2.1](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf). Dream uses the opposite naming ("acyclic and cyclic subgraphs for which no match is found are called proper and improper intervals"), which matches Muchnick's: the leftover kinds are "proper" (acyclic) and "improper" (cyclic). [V] — [Dream §II-A](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Allen's interval: for a header `h`, the maximal single-entry subgraph in which `h` dominates every node and every cycle passes through `h`. Replacing each interval with one node gives the derived graph; repeating gives the derived sequence, and a graph is reducible iff the sequence ends in one node. [B] — F. E. Allen, "Control flow analysis", SIGPLAN Notices 5(7), 1970; J. Cocke, "Global common subexpression elimination", same issue.
- Sharir's structural analysis and Muchnick's textbook version (Advanced Compiler Design and Implementation, 1997, §7.7, cited by Phoenix as "[32, p. 203]") use these region types. Acyclic: block (sequence), if-then, if-then-else, case/switch, proper. Cyclic: self-loop, while-loop, natural loop, improper. Each step tries the acyclic types at the node, then the cyclic ones; a successful match is collapsed and the dominator and post-order information is updated. [B] — M. Sharir, "Structural analysis: a new approach to flow analysis in optimizing compilers", Computer Languages 5(3–4), 1980.
- Muchnick's schemas mostly preserve semantics, "but the natural loop schema is one that does not": a single-entry loop with several exits collapses into one node with several exit edges, which no longer records which exit fires under which condition. [V] — [Phoenix §3](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- Cifuentes' dcc structures with interval analysis and adds four region patterns for the shape that short-circuit evaluation of compound conditions (`x ∨ y`) leaves in the graph; "Obviously, this method fails if no match to these patterns is found." [V] — [Dream §IV and §VIII](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Cifuentes' thesis structures loops from intervals (pre-tested, post-tested and endless loops, with the loop header from the interval and the follow node from the latch) and 2-way and n-way conditionals from the immediate post-dominator of the branch node. Conditionals are structured innermost first, and an unresolved branch becomes a goto. [B] — C. Cifuentes, Reverse Compilation Techniques, PhD thesis, Queensland University of Technology, 1994; "Structuring decompiled graphs", CC 1996.
- Vanilla structural analysis cannot structure loops that contain `break` or `continue`. Engel et al.'s SESS (single exit, single successor) analysis turns such exits into tail regions, but "the detection of tail regions, is left unspecified", and Phoenix's implementation of it often stopped making progress "when regions do not have an unambiguous successor". [V] — [Phoenix §2.1](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- Boomerang's structurer is based on parenthesis theory: "Although faster than interval analysis, it recovers less structure." [V] — [Dream §VIII](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- "Currently, all existing methods … agree that inner structures should be processed before outer structures", implemented by visiting nodes in post-order. [V] — [SoK, IEEE S&P 2025, §4.3](https://oaklandsok.github.io/papers/behner2025.pdf)

### Inferences

- The reduction loop has the shape of mentalc's level ladder: collapse a matched group of lower steps into one upper step labelled with the pattern, and repeat at the next level. The difference is that a decompiler collapses inside one CFG until a single node is left, while mentalc stops at each level and keeps that level as a record.
- Structural analysis has been kept for 45 years because each reduction is local, checkable and labelled with the schema that justified it. That suits a model in which every record is anchored: a collapsed node can carry the schema name and the lower nodes it covers.
- The "proper/improper region" leftover is the important idea for mentalc: a step kind that means "this matched no pattern", stated as such rather than forced into a pattern.

### Gaps

- Sharir 1980, Allen 1970 and Cifuentes 1994 were not opened (paywalled or not found as text); their details above are [B] or come through Phoenix and Dream.

## Phoenix: semantics-preserving schemas and iterative refinement

### Takeaway

Phoenix makes two changes to structural analysis. First, schemas match the boolean conditions on edges as well as the shape, so a reduction can never claim a construct whose behavior differs from the graph's. Second, when the loop is stuck, it removes one edge and replaces it with an explicit tail region (goto, break or continue), choosing the edge by a fixed preference order. Then matching resumes. The goto is an honest residue that keeps the result correct and lets matching continue.

### Cited Findings

- The reduction that breaks semantics: a natural loop with exits on `x = 1` and `y = 2` collapses into one node with two exit edges, the resulting diamond matches if-then-else, and the result "would be correct for data flow analysis, which only depends on reachability". But when both conditions hold, the original takes the first exit, while "in the middle graph, both exit edges can be taken." [V] — [Phoenix §3](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- "Our schemas match both shape and the boolean predicates that guard execution of each node … shape alone is not enough to distinguish which control structure should be used". A switch on `x = 2` and `x = 3` can have the diamond shape of an if-then-else, but if-then-else requires the outgoing conditions to be inverses. [V] — [Phoenix §3.2](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- The schemas: acyclic `Seq[n1…nk]`, `IfThen`, `IfThenElse[c, n, nt, nf]`, `Switch` and `IncSwitch` (a switch with a fall-through or bypassing default); cyclic `While[c,h,s,b]`, `DoWhile[c,h,b]` and `NatLoop[h,b,e1…ek]`. The natural-loop schema deliberately has no outgoing edges, because it is emitted as `while (1) {…}` and every exit must be an explicit tail region (goto, break or continue) inside it. [V] — [Phoenix §3.2, §3.5, Tables 3–4](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- The loop at a node `n`: try the acyclic schemas; if none matches and the region is a switch candidate, refine it into a switch. If `n` is cyclic, try the cyclic schemas, and if they fail, refine `n` into a loop. If neither matching nor refinement makes progress, skip `n` for this iteration. "If there is an iteration in which all nodes are skipped … then the algorithm employs a last resort refinement". [V] — [Phoenix §3.1](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- Refinement means virtualizing an edge: remove `(n1, n2)`, put a fresh label at `n2`, and collapse `n1` into a tail region that ends in `goto l`, `break` or `continue`. "Because the tail region explicitly represents the control flow of the virtualized edge, it is safe to remove the edge from the graph and ignore it when doing future pattern matches." [V] — [Phoenix §3.3](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- Tie-breaking rules, each stated as a fixed preference:
  - Several loops sharing a header: "The loop with the smallest loop body is reduced first", because there is no schema for nested loops.
  - Several loop entrances: keep "the one with the most incoming edges" and virtualize the rest.
  - Loop type: an exit from the header makes a While candidate, an exit from the back-edge source a DoWhile candidate, and otherwise "any exit edge is selected" and the loop is a NatLoop candidate.
  - Switch successor: the immediate post-dominator of the head if it succeeds a case, otherwise the non-case successor "that … has the highest number of incoming edges from case nodes".
  - Last resort: prefer to remove "edges whose source does not dominate its target, nor whose target dominates its source", that is, edges that cut across the dominator tree.

  [V] — [Phoenix §3.4–3.7](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- A switch candidate is a near-miss: a region "that would match a switch schema in Table 3 but contain extra edges" (extra incoming edges, or several successors). Phoenix makes it match by virtualizing exactly the edges that break the schema. [V] — [Phoenix §3.4](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- Results on 107 coreutils programs: 60 utilities pass the full coreutils test suite against 28 for Hex-Rays (114% more). Semantics-preserving schemas raised correctness from 46 to 60. 8,676 functions were structured with 40 gotos; without iterative refinement there were 1,229 gotos ("30× more"); without the new loop-membership definition, 73. Hex-Rays emitted 51 on the same set. [V] — [Phoenix §4, Table 6](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- Loop membership was redefined: the lexically contained nodes are the loop body plus nodes dominated by the header and not reachable from the loop's successor without passing the header. This puts a `break` branch inside the loop instead of producing a goto. [V] — [Phoenix §3.6, Fig. 5](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)

### Inferences

- Semantics preservation maps onto mentalc directly. A move pattern that matches only shape (read, branch, write) could collapse a read-test-write into "claim the job" even when the write is unconditional. That repeats Phoenix's natural-loop error: correct reachability, wrong behavior under interleaving. A mentalc pattern must match the evidence as well as the node kinds: the guard on the write, the transaction, the lock. This is the same test the specification applies to a level ("nothing those steps do can change what is seen at the step's own level").
- Phoenix's "virtualize the edge that breaks the schema" is a near-miss report produced as a side effect: the virtualized edges are exactly the difference between the region and the schema. A mentalc pattern library could record, for each near-miss, which required element was missing or which extra edge was present, anchored to the code.
- Phoenix's preference rules show that ambiguity in practice is settled by fixed, documented rules (smallest body first, most incoming edges, cross-dominator edges first). They are deterministic, which suits mentalc, but they are heuristics. Under fail rather than degrade, mentalc should report as a diagnostic any choice that a tie-break settled, instead of hiding it.

### Gaps

- Phoenix gives no measurement of how often several schemas matched the same node, so the frequency of real ambiguity is unknown.

## Dream, Dream++, rev.ng, SAILR, Ghidra, Hex-Rays and Binary Ninja: pattern-independent structuring and the goto as fallback

### Takeaway

Dream replaced the schema library with logic. It computes for every node the condition under which it runs, writes the region as `if (cond) node` for each node, and simplifies into if/else, switch and loops. It reached zero gotos, paying in duplicated conditions and structure that does not resemble the source. rev.ng reaches zero gotos by duplicating code. SAILR (2024) argues that zero gotos is the wrong goal. Many gotos are in the source, the spurious ones come from specific compiler optimizations, and the right move is to recognize and invert those optimizations, keeping a goto wherever the source had one. Measured by edit distance to the source CFG, pattern matching with gotos (SAILR, Hex-Rays, Phoenix: about 22.5) is twice as faithful as goto-free structuring (Dream 46, rev.ng 71).

### Cited Findings

- Dream's critique of patterns: structural analysis and its extensions "rely on a predefined set of region patterns to structure the CFG. For this reason, they cannot structure arbitrary graphs without using goto statements. Our approach is fundamentally different in that it does not rely on any patterns." [V] — [Dream §VIII](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Reaching conditions: over the slice between a region's head and its nodes, in topological order, `cr(ns, n) = ⋁_{v ∈ Preds(n)} (cr(ns, v) ∧ τ(v, n))`, where `τ` is the edge's condition, followed by logical simplification. [V] — [Dream §IV-A](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Acyclic regions: "any directed acyclic graph has at least one topological ordering". The initial AST is `if (cr(h,n1)) {n1}; …; if (cr(h,nk)) {nk}`, which three refinements then rewrite:
  - condition-based refinement groups nodes under `c ∧ R` and `¬c ∧ R`, with pairs of complementary conditions given priority as if-then-else;
  - condition-aware refinement finds switch constructs from the comparisons behind each logical variable;
  - reachability-based refinement builds cascading if-else from reachability between nodes.

  [V] — [Dream §IV-B](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Dream's cyclic part makes abnormal loops single-entry and single-successor through semantics-preserving transformations that add a structuring variable and conditions. It then infers the loop type (while, do-while, endless) with a set of refinement rules, such as turning an endless loop whose body starts with a break-condition into a while. [B] — the two pages covering this (§IV-C, §V) failed to extract from the [Dream PDF](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf); the SoK confirms that Dream "duplicates certain conditions and introduces new variables and conditions" [V] — [SoK §2](https://oaklandsok.github.io/papers/behner2025.pdf).
- Dream's correctness test: 1,530 coreutils functions (219 gotos in the preprocessed source) were re-structured from their CFGs, swapped in, and passed every coreutils test, leaving 0 gotos. In the head-to-head comparison over the unique functions all three decompilers handled (1,821), Dream emitted 0 gotos against 4,231 for Phoenix and 2,949 for Hex-Rays, and 107k lines against 164k and 135k. [V] — [Dream §VII, Tables II–III](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Dream also recognizes idioms after structuring: if-assignments become ternaries, while loops become for loops, inlined `strcpy`/`strlen`/`strcmp` are outlined back into calls, and variables are named after the API parameters they feed. [V] — [Dream §VI](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Dream++ adds readability transformations to Dream. In a user study on six malware-analysis tasks, participants solved about three times as many tasks with Dream++ as with Hex-Rays and twice as many as with Dream. [S] — [Fraunhofer record](https://publica.fraunhofer.de/handle/publica/395828), [S&P 2016 slides](https://www.ieee-security.org/TC/SP2016/slides/yakdan.pdf)
- rev.ng's Combing aims at generality ("applicable on any arbitrary CFG"), no gotos, and idiomatic C. Preprocessing enforces single entry, single successor and a single retreating edge for each loop (a strongly connected set found from a back edge), mapping exits to `break` and retreating edges to `continue` so the loop becomes a virtually acyclic region. The comb then enforces that "for each node between the conditional node itself and its immediate post-dominator, the conditional node must dominate all such nodes. If this is not true, we introduce clone nodes". [V] — [rev.ng AsiaCCS 2020 slides](https://rev.ng/downloads/asiaccs-2020-presentation.pdf). The paper reports 40–50% less added cyclomatic complexity than the tools it compares against. [S] — [Polimi record](https://re.public.polimi.it/handle/11311/1147248)
- SAILR's thesis: "the measure of binary decompiler success is not to eliminate all gotos … but to get as close as possible to the original source code". Linux 6.1 contains 3,754 gotos. Spurious gotos come from compiler optimizations "that occur at all optimization levels (17% in non-optimized compilation)". [V] — [SAILR, USENIX Security 2024, abstract](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- SAILR traced each of the 3,002 gotos in Hex-Rays 8.0's output for 1,150 coreutils functions (GCC 9.5, -O2) to a GCC transformation: jump threading, common subexpression elimination, switch conversion, cross jumping, software thread cache reordering, loop header optimizations, builtin inlining, switch lowering and non-returning functions. It groups them as irreducible statement duplication (ISD: one source statement becomes several copies), irreducible statement condensing (ISC: several statements merged and joined by jumps) and a miscellaneous group. [V] — [SAILR §3.3](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- The problem with patterns, in SAILR's words: "because compiler optimizations create novel graph schemas, there are more graph schemas in real-world binaries than one can reasonably enumerate", so pattern matchers virtualize edges into spurious gotos. Goto-less algorithms "create new control-flow structures that are functionally equivalent … [that] often do not match the source's because they can introduce new or duplicated code". [V] — [SAILR §2](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- SAILR's pipeline runs to a fixed point: region identification (single-entry single-exit regions in reverse topological order, from Dream); schema matching per region (from Phoenix; "when SAILR fails to match a region against any known graph schemas, it will virtualize an edge … replacing the source jump statement with a goto"); region simplification; and deoptimization. Deoptimization search "is goto-guided … we only search the blocks around a goto edge when finding candidates." [V] — [SAILR §4.1.2, §4.2](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- Results on 7,355 functions from 26 Debian packages, whose source has 1,367 gotos:

  | Structurer | Gotos | CFG edit distance (mean) | Boolean expressions |
  |---|---|---|---|
  | Source | 1,367 | 0 | 6,180 |
  | SAILR | 2,673 | 22.64 | 3,980 |
  | Hex-Rays | 6,115 | 22.52 | 4,279 |
  | Ghidra | 6,575 | 25.5 | 4,850 |
  | Phoenix | 8,497 | 22.64 | 2,685 |
  | Dream | 0 | 45.99 | 43,661 |
  | rev.ng | 0 | 71.29 | 2,003 |

  rev.ng also emitted 166,798 calls against 53,995 in the source, from duplicated code. [V] — [SAILR Table 3](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- Prior structurers were not runnable: Phoenix was never open-sourced, the open-source Dream did not build, and the rev.ng alpha crashed on most coreutils binaries, so SAILR reimplemented all three in the angr decompiler. [V] — [SAILR §8.1](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- Ghidra: `CollapseStructure::collapseInternal` ("Collapse everything until no additional rules apply") tries, for each block in order, `ruleBlockGoto`, `ruleBlockCat`, `ruleBlockProperIf`, `ruleBlockIfElse`, `ruleBlockWhileDo`, `ruleBlockDoWhile`, `ruleBlockInfLoop` and `ruleBlockSwitch`, restarting whenever one applies. `ruleBlockIfNoExit` and `ruleCaseFallthru` run only when nothing else applies. When everything is stuck, `selectGoto` takes the first valid edge from a `likelygoto` list computed by a `TraceDAG` over the innermost loop first. The bad edge is scored by sibling count, terminal exit, distance between branch points and depth, with exits prioritized for removal "middle exit at front, head exit, then tail exit". If no edge can be chosen, it throws "Could not finish collapsing block structure." [V] (fetched source, summarized by the fetch tool) — [Ghidra blockaction.cc](https://raw.githubusercontent.com/NationalSecurityAgency/ghidra/master/Ghidra/Features/Decompiler/src/decompile/cpp/blockaction.cc); class list at [Ghidra Doxygen](https://ghidradocs.com/11.4_PUBLIC/docs/DecompilerDoxygen/html/blockaction_8hh.html) [S]
- The 2025 SoK classifies the systems. Pattern matching with gotos only: Ghidra, Phoenix, radare2, RetDec. Pattern matching with gotos and some code duplication: Hex-Rays, and SAILR with (de)duplication. Pattern-independent without gotos: Dream and dewolf (no code duplication), rev.ng (with code duplication). Pattern-independent with all options including gotos: Binary Ninja. [V] — [SoK Table 1](https://oaklandsok.github.io/papers/behner2025.pdf)
- The SoK's four challenges: which subgraphs are resolvable, how to handle the non-resolvable ones, in what order to resolve them, and practicality. The only four options for a non-resolvable region are "introducing gotos, duplicating code or conditions, and adding structural variables", and "It is practically impossible to determine which option results in the best output for the entire function." On order: "only because a decision is locally optimal does not imply that it also leads to overall optimal function output", and there may be "an exponential number" of candidate regions. [V] — [SoK §4, §4.2, §4.3](https://oaklandsok.github.io/papers/behner2025.pdf)
- On goto use: "there are valid reasons to utilize them, such as exiting an inner loop, but they can significantly aggravate manual analysis". [V] — [SoK §4.2](https://oaklandsok.github.io/papers/behner2025.pdf)
- angr made SAILR its default structurer soon after publication (angr 9.2, 2024). [B]

### Inferences

- The arc from Dream to SAILR is the main lesson for mentalc. Forcing every region into a structured construct (Dream, rev.ng) gives complete but unfaithful output: duplicated conditions and code, and twice the edit distance to the source. Recognizing why a region does not match (SAILR: which optimization made it) and inverting that cause gives faithful output and keeps the honest gotos. In mentalc, generic closing rules are the pattern-independent side: they always cut. A pattern library is the SAILR side: it names what it recognizes and leaves the rest visibly unmatched.
- SAILR's compiler-awareness has a direct analog in mentalc's packs. A framework lowers one intent ("claim this row") into several code shapes: a filtered `UPDATE … WHERE status='PENDING'`, `select_for_update` and then a write, a Redis `SET NX`, a compare-and-swap loop. As SAILR knows how GCC lowers source into CFG shapes, a pack can state the shapes its library produces for one intent, giving the lifting patterns per pack.
- SAILR's goto-guided search shows that near-miss search can be confined to where something already looks wrong. For mentalc, that means searching for "claim missing its guard" only around moves whose verdict is non-atomic, not over the whole graph.
- Ghidra shows the engineering fallback: a fixed rule order, a heuristic edge choice, and an exception when even that fails. That fits "fail rather than degrade" only if the heuristic choice is reported. Ghidra reports nothing; it just emits the goto.

### Gaps

- No source here measures how readable Ghidra's or Binary Ninja's current structurers are; the SoK assessment is partly "our observations".
- Whether SAILR's inverse-optimization patterns are ever ambiguous (two optimizations explaining one goto) is not stated in the parts read.

## Pattern-based vs pattern-independent structuring: tradeoffs, and what each says for mentalc

### Takeaway

Pattern-based structuring has bounded coverage, local and explainable decisions, and an honest residue (gotos), and it is closest to the source when the patterns reflect how the code was produced. Pattern-independent structuring has total coverage and provable semantic equivalence, but its output is further from the source, with duplicated conditions or code, and its region sizes and conditions can grow large. For mentalc the two are not alternatives. Keep a pattern-independent base that guarantees coverage (the closing rules), and on top of it a pattern library that names and refines what it recognizes, with everything else left as a visible residue.

### Cited Findings

- Coverage: pattern matchers "cannot structure arbitrary graphs without using goto statements" [V] — [Dream §VIII](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf); "there are more graph schemas in real-world binaries than one can reasonably enumerate" [V] — [SAILR §2](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf).
- Correctness: both families can be semantics-preserving. Phoenix's correctness depends on condition-aware schemas (46 → 60 passing utilities), and Dream's structured coreutils passed every test. [V] — [Phoenix §4](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf), [Dream §VII](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf). SAILR's taxonomy marks every structurer it lists except mirtoc as condition-aware. [V] — [SAILR Table 1](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- Readability and faithfulness: goto-free structuring doubles or triples the edit distance to the source (Dream 45.99, rev.ng 71.29, against about 22.5 for pattern matchers) and multiplies boolean expressions (Dream 43,661 against 6,180 in the source). [V] — [SAILR Table 3](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf). Yet in Dream's own user study a goto-free decompiler beat Hex-Rays on task success. [S] — [Dream++ record](https://publica.fraunhofer.de/handle/publica/395828)
- Practicality: Dream "Missing SISO regions by only considering the dominance region, which results in large regions & conditions causing long computations"; dewolf "Always structuring the whole smallest (n > 2) SISO region, which can lead to large regions & conditions causing long computations"; rev.ng may produce "output containing a lot of duplicated code". [V] — [SoK Table 1](https://oaklandsok.github.io/papers/behner2025.pdf)
- Order dependence is shared by both families: every method processes inner before outer, but choosing among regions at one entry is not locally decidable. In the SoK's example, Phoenix and SAILR restructured only one infinite loop where two nested loops were possible, and Ghidra and Hex-Rays emitted gotos. [V] — [SoK §4.3](https://oaklandsok.github.io/papers/behner2025.pdf)

### Inferences

- mentalc's closing rules (a move closes at a write to shared state, an activation closes when the entity must wait) are pattern-independent in Dream's sense. They are stated over properties (a write, a wait point, a terminal state) rather than shapes, so they cover every step and need no library. That is why the coverage check (every lower step class mapped or marked support) can be guaranteed today.
- What they cannot do is say what a step is. A closing rule cuts "the steps between two writes"; it cannot say "this is a claim". A pattern library adds that, the way schema matching labels a region `While` rather than just "a single-entry region". Following SAILR, the label should come from a pattern tied to how the code was produced (framework idioms from packs), not from an LLM.
- The goto analog in mentalc is an upper step that no pattern names, which stays a generic "closed by rule" step. It must remain a first-class, visible step kind, not be absorbed into the nearest pattern. Dream's lesson is that forcing everything into the vocabulary costs faithfulness.
- Because closing rules already guarantee coverage, a pattern library in mentalc never has to "make progress", so it needs no Phoenix-style last-resort edge removal. Patterns can be strict (match or not), and nothing is lost when one fails.

### Gaps

- No study compares pattern libraries against property-based cutting for anything other than C control flow; the transfer to effect graphs is inference.

## Graph rewriting and graph grammars: DPO/SPO, tools, matching cost, confluence, termination and critical pairs

### Takeaway

A pattern library over the effect graph is a graph rewriting system: each pattern is a rule `L → R` (a lower subgraph replaced by an upper step), optionally with negative application conditions ("and no guard on the write"). Graph transformation theory supplies the two checks a pattern library needs before it ships. Critical pair analysis lists every pair of rules that can claim overlapping nodes or disable each other. Layering gives termination. Matching is NP-complete in general, but cheap for small patterns anchored at a known node.

### Cited Findings

- In the double-pushout (DPO) approach a rule is a span `L ← K → R`. A match of `L` may delete only what is not in `K`, and only if the gluing condition holds: no dangling edges, and no identification of a deleted item with a kept one. Single-pushout (SPO) drops the gluing condition and deletes dangling edges implicitly. Negative application conditions (NACs) forbid a match when a given extension of `L` exists. [B] — Ehrig, Ehrig, Prange, Taentzer, Fundamentals of Algebraic Graph Transformation, Springer 2006.
- AGG's critical pair analysis: "Critical pairs are found by overlapping the left-hand sides in all possible ways", in a minimal graph that glues the two left-hand sides. Conflicts are delete-use (one application deletes an object in the other's match), produce-forbid (one application creates a structure that another's NAC forbids) and attribute change. The set "represents precisely all potential conflicts". Rules are then sorted into conflict-free and conflicting sets, and with NACs, overlaps of a left-hand side with part of a NAC must be considered too. [V] — [AGG critical pairs page](https://user.tu-berlin.de/o.runge/AGG/WWW/critical_pairs.html)
- AGG computes critical pairs only within a layer for layered grammars; the analysis "may take time, even for one particular rule pair"; type-graph multiplicity bounds can reduce the number of pairs drastically. [V] — [AGG critical pairs page](https://user.tu-berlin.de/o.runge/AGG/WWW/critical_pairs.html)
- The critical pair lemma: a system is locally confluent if all its critical pairs are strictly confluent, and with termination, local confluence gives confluence (Newman's lemma). In general, though, confluence is undecidable even for terminating graph transformation systems, and joinability of the critical pairs alone is not enough, which motivates "strong joinability". [S] — [Plump, ECEASST](https://eprints.whiterose.ac.uk/195071/1/Plump.ECEASST.10.pdf), [Checking GTS for confluence](https://www.academia.edu/72673358/Checking_Graph_Transformation_Systems_for_Confluence)
- GROOVE implements critical pair detection for single-pushout systems. [S] — [University of Twente](https://fmt.ewi.utwente.nl/media/106.pdf). GROOVE's main use is exploring the full state space that a rule system generates from a start graph. [B]
- Termination of layered graph grammars (Ehrig et al., ICGT 2004/2006): rules are assigned to layers that each deletion or creation layer condition makes finite, layers run in order to a fixed point, and the criteria are checked statically. [B]
- GrGen.NET compiles patterns to search plans chosen by a cost model "taking the present host graph into account" (Batz, Kroll, Geiß, AGTIVE 2008), supports NACs (`negative` blocks), and its current release is 8.1 (May 2026). [S] — [GrGen search plans](https://i44vm2.informatik.kit.edu/uploads/publikationen/jakumeit10sttt.pdf), [GrGen (Wikipedia)](https://en.wikipedia.org/wiki/GrGen). A general framework treats search-plan operations as cost-weighted predicates, so that NACs and attribute checks run "early (but not unnecessarily early)". [S] — [ECEASST](https://eceasst.org/index.php/eceasst/article/download/1406/1529/1540)
- PROGRES (Schürr, 1990s) is a typed graph rewriting language with control structures, and its rules carry positive and negative conditions; it is no longer maintained. [B]
- Subgraph isomorphism, and its error-correcting variant, is NP-complete. [S] — secondary citation of Garey and Johnson in [Bunke's framework paper](https://link.springer.com/doi/10.1007/BFb0033223). For a fixed pattern of `k` nodes, naive matching is `O(n^k)`, and anchoring one pattern node to a known host node with bounded degree makes it near-linear in practice (Ullmann 1976, VF2 2004). [B]
- Structural analysis is itself a graph rewriting system whose result depends on order: Phoenix needs "smallest loop body first" because there is no nested-loop schema, Ghidra fixes a rule order and delays two rules until nothing else applies, and the SoK shows locally optimal choices can be globally worse. [V] — [Phoenix §3.5](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf), [Ghidra blockaction.cc](https://raw.githubusercontent.com/NationalSecurityAgency/ghidra/master/Ghidra/Features/Decompiler/src/decompile/cpp/blockaction.cc), [SoK §4.3](https://oaklandsok.github.io/papers/behner2025.pdf)

### Inferences

- Each mentalc level is a natural layer: patterns at the move layer read effect nodes and produce moves, patterns at the activation layer read moves, and so on. Because no rule consumes what it produces, layer by layer, termination comes free, as in layered grammars.
- Critical pair analysis is the right check for the pattern library itself, run when the library or a pack changes, not on each user build. Two patterns that can claim the same write node are a conflict. Either one has a NAC that excludes the other (`claim` requires a guard, `blind-claim` forbids one), or the library is ambiguous and the check fails with both pattern names. That turns "several patterns match" from a runtime heuristic (Phoenix, Ghidra) into a library error, which is how "fail rather than degrade" would handle it.
- NACs are the natural notation for near-misses. "Claim" is: read state variable `s`, branch on `s = PENDING`, write `s := RUNNING` with guard evidence. Its near-miss is the same left-hand side with a NAC on the guard. Matching the near-miss rule is an exact match, which keeps it deterministic and anchored; it is not approximate matching.
- Matching cost is not a concern at mentalc's scale. Behaviors are per-port graphs of tens to hundreds of nodes, and patterns can be anchored at the node that closes a step (the write that closes a move), so a search-plan engine is not needed.
- External graph-transformation tools (AGG and GROOVE in Java, GrGen in .NET) do not fit a Rust compiler that runs nothing external. Their value is the theory (CPA, NACs, layering), which is small enough to implement for mentalc's restricted pattern language.

### Gaps

- The ICGT termination criteria and the DPO definitions above are [B]; the primary texts were not opened.
- No source was found on CPA run time for rule sets of realistic size (tens to hundreds of rules).

## Tree-pattern matching and BURS: cost-based tiling, and lifting as instruction selection run backwards

### Takeaway

Instruction selection solves the dual problem: cover an IR tree with machine-instruction patterns. Overlapping matches are resolved by dynamic programming to the minimum-cost cover, bottom-up labelling then top-down reduction, which is deterministic and optimal for trees. DAG covering is NP-complete, and production compilers use greedy heuristics. The reverse direction exists in two forms: lifters derived from a compiler's own instruction descriptions (LISC), and decompilers that invert specific compiler passes (SAILR, Dream's outlining of inlined calls). The fact that carries over: one high-level operation has many minimal low-level patterns, so a pattern library must hold all of them, and a missing pattern is a silent miss.

### Cited Findings

- iburg reads a burg specification and generates a hard-coded matcher that does the dynamic programming at compile time. BURS moves the dynamic programming into table generation at compile-compile time, which makes matching fast but requires constant costs; iburg allows dynamic cost computation and is simpler. The generated matchers run up to 25 times faster than Twig's. burg and iburg produced VAX, MIPS and SPARC code generators for lcc. [S] — [Fraser, Hanson, Proebsting, LOPLAS 1992 (Arizona record)](https://experts.arizona.edu/en/publications/engineering-a-simple-efficient-code-generator-generator/), [typeset.io copy](https://typeset.io/papers/engineering-a-simple-efficient-code-generator-generator-vpsqom5o78). Proebsting's TOPLAS 1995 paper gives the BURS table-generation algorithm. [S] — [BURS automata generation](https://experts.arizona.edu/en/publications/burs-automata-generation/)
- The algorithm: a bottom-up pass labels each node, for each nonterminal, with the cheapest rule deriving it and its cost (the rule's cost plus its children's best costs), closing over chain rules `nt1 ← nt2`. A top-down pass from the goal nonterminal then emits the chosen rules. Ties go to the first rule in the specification. A tree for which no rule derives the goal nonterminal has no cover, and lcc treats that as an error in the specification, not a recoverable case. [B] — Pelegrí-Llopart and Graham, "Optimal code generation for expression trees: an application of BURS theory", POPL 1988; Fraser, Hanson, Proebsting 1992.
- Instruction selectors "match the pattern of each rule in the library to the IR … Then, the selector computes a pattern cover of the program". One x86 instruction can have several minimal IR patterns (`andn`: `∼x&y`, `x⊕(x|y)`, `y⊕(x&y)`, `y−(x&y)`), "Since any of these patterns might occur in a program, the instruction selector needs all rules to ensure a match." "If a pattern is missing, the instruction selector cannot generate the corresponding instruction". [V] — [Buchwald, Fried, Hack, CGO 2018, §1, §2.4](https://i44vm2.informatik.kit.edu/uploads/publikationen/buchwald18cgo.pdf)
- Optimal DAG covering is NP-complete without restricting the ISA; LLVM, HotSpot and libFirm restrict themselves to DAG or tree patterns with "some greedy heuristics for selecting an appropriate covering". [V] — [CGO 2018 §2.1](https://i44vm2.informatik.kit.edu/uploads/publikationen/buchwald18cgo.pdf)
- Synthesizing the rule library from formal semantics found 31,612 instruction-selection rules missing in GCC and 36,365 missing in Clang. [V] — [CGO 2018 §1](https://i44vm2.informatik.kit.edu/uploads/publikationen/buchwald18cgo.pdf)
- LISC learns assembly-to-IR (GCC RTL) translation from the instruction semantics already in GCC's code generator, for x86, ARM and AVR: a lifter derived by running instruction selection's knowledge backwards. [S] — [Hasabnis and Sekar, ASPLOS 2016](https://researchr.org/publication/HasabnisS16), [LISC page](https://www.seclab.cs.sunysb.edu/seclab/lisc)
- SAILR's deoptimizations are passes run in reverse: they merge ISD-duplicated blocks by redirecting predecessors, and re-duplicate ISC-condensed blocks, using "information derived from GCC 9.5 to perform the reverse actions of these optimizations". [V] — [SAILR §4.2, §5](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- Dream's post-structuring idiom recognition outlines inlined library functions (`strcpy`, `strlen`, `strcmp`) back into calls. [V] — [Dream §VI](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf)
- Chang et al.'s modular decompilation architecture is "a series of decompilers connected by intermediate languages". [V] — [Dream §VIII](https://www.ndss-symposium.org/wp-content/uploads/2017/09/11_4_2.pdf). Hex-Rays lifts through microcode "maturity levels", and angr through its AIL, each an IL between machine code and C. [B]

### Inferences

- Cost-based tiling answers "several patterns match" by optimization, not by rule order. It is deterministic given fixed costs and tie-breaks, but the costs are a judgment hidden in numbers. For mentalc, where a chosen label is a claim about the system, an unexplained cost choice between two meanings ("claim" or "update status") is worse than a reported ambiguity. Keep dynamic programming for cases where the alternatives are equivalent readings at different grain, and make semantic conflicts library errors found by critical pair analysis.
- The `andn` fact is the strongest warning for a mentalc pattern library. "Claim a job" will have many minimal lower-level forms across ORMs, drivers and queues. A pattern library that misses one does not fail: the step falls back to a generic closed step and no finding is made. Two remedies follow from this section. The pattern sets per pack should be generated from a pack's stated semantics (as the CGO paper synthesizes rules), and the resolution report should count, per level, the steps that matched no pattern, as it counts unresolved sites today.
- Lifting through a series of ILs (Chang et al., Hex-Rays maturity levels, angr AIL) supports the owner's idea of one IL per level. Each lifting pass reads one IL and writes the next, and is tested on its own.
- BURS is tree-only, and mentalc's behaviors are DAGs with branches and, through retries and loops, cycles. Tiling is usable only after the region structure is known (inside a single-entry single-exit region, or on the expression trees of predicates), not on the whole graph.

### Gaps

- The iburg paper was a scanned PDF with no text layer; its details above are [S] or [B].
- No source was found for a decompiler that uses BURS-style dynamic programming in reverse for control-flow or idiom lifting. "Instruction de-selection" turned up no specific system. Superoptimizer-derived lifting rules turned up only the forward direction (CGO 2018).

## Approximate and inexact graph matching: graph edit distance and near-miss detection

### Takeaway

Approximate matching (graph edit distance, error-tolerant subgraph isomorphism) is NP-hard. In practice it is used for measurement (SAILR's distance to source) or similarity search, not to report findings. The working near-miss detectors are exact. Phoenix's "switch candidate" is a schema plus extra edges. SAILR's deoptimizations are exact patterns searched only around gotos. Engler's deviance checking infers rules from what code usually does and reports exact violations, ranked by statistics. For mentalc, a near-miss should be an exact match of a declared broken variant of a pattern, anchored to the missing or extra element.

### Cited Findings

- Graph edit distance uses deletion, insertion and substitution (label change) of nodes and edges; computing it is NP-hard, and error-tolerant subgraph isomorphism is NP-complete. Bunke related graph edit distance to the maximum common subgraph. [S] — [Bunke, "Error-tolerant graph matching: a formal framework and algorithms"](https://link.springer.com/doi/10.1007/BFb0033223), [Bunke, graph matching notes](https://www.ai.rug.nl/ki2/literature/graphmatch-bunke.pdf)
- SAILR: "computing an exact GED is NP-hard … exact GED is usually too expensive to run on graphs with more than 12 nodes", and upper-bound estimators "rarely return zero" on identical graphs. CFGED decomposes along single-entry single-exit regions, uses exact distance on small regions and approximate distance only "as the last resort", and sums. On 506 coreutils functions with under 12 nodes it fell between the exact and the maximum, and was exact on 64%. [V] — [SAILR §7.2](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- SAILR validated the metric against human-written decompilations from the Decomperson study: participants' distance to source fell as their submissions improved. [V] — [SAILR §7.1](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)
- Phoenix's switch candidate, a region "that would match a switch schema … but contain extra edges", is refined by virtualizing exactly the offending edges. [V] — [Phoenix §3.4](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)
- Engler et al. infer programmer "beliefs" from code and cross-check them. MUST beliefs are directly implied (a dereference implies non-null), and any contradiction is an error. MAY beliefs are patterns that might be coincidence; they are ranked statistically (a pattern followed 999 times out of 1,000 makes the one exception a likely bug). Six checkers found hundreds of bugs in Linux and OpenBSD. [S] — [Engler et al., SOSP 2001](https://www.sosp.org/2001/papers/yu-chen.pdf) (PDF downloaded, but its font encoding defeated text extraction)
- Error-tolerant matching is used in symbol recognition and pattern recognition, where inputs are noisy. [S] — [Symbol recognition by error-tolerant subgraph matching](https://www.academia.edu/59799157/Symbol_recognition_by_error_tolerant_subgraph_matching_between_region_adjacency_graphs)

### Inferences

- Graph edit distance fits mentalc only as a metric, and that is a real use: measuring how close a lifted level is to a hand-written reference ladder for report-jobs or rq, as SAILR measures closeness to source. SAILR's region decomposition (exact distance per region, summed) also suits mentalc, since steps nest.
- As a finding mechanism, edit distance fails mentalc's principles. The result depends on edit costs nobody can justify; approximations are not stable under small changes; "distance 1 from claim" does not say which element is missing unless the edit script is kept; and the search is exponential. A declared near-miss rule (the pattern with a NAC) gives the same finding exactly, with the missing element named and anchored.
- Engler's split maps onto mentalc. MUST-style near-misses come from declared patterns: the pack says that an at-least-once channel with a status-test-then-write must be guarded, so an unguarded one is a finding. MAY-style near-misses come from the repository itself: if nine of ten writes to `report.status` are guarded and one is not, the one is suspicious. The MAY form is statistical and would need labelling as a prediction, as the specification already labels static findings until `mentalvm` confirms them with a witness.
- The finding a near-miss yields in mentalc is concrete: "the move at `generate_report` matches the claim pattern except for guard evidence on the write", anchored at the write, with the pattern's name and the missing element. The existing atomicity check (a non-atomic move on a state variable another activation can write) already behaves like one such near-miss rule. A pattern library generalizes it to other intents (idempotent create, lease renewal, outbox publish).

### Gaps

- No source was found that uses graph edit distance or error-tolerant matching to report bugs (as opposed to clones or similarity) with a measured false-positive rate.

## Fit for mentalc

The constraints used to rank: the result is a pure, deterministic function of the code; every record is anchored; fail rather than degrade; no LLM for facts or boundaries; every lower step covered (mapped or marked support). Ranked from best fit to worst.

1. **A post-order reduction loop over a condition-aware pattern library, with an explicit residue.** This is Phoenix's design without last-resort refinement. Patterns match node kinds and the evidence on them (guard, lock, transaction, predicate), not shape alone. Inner levels come first, and a matched group collapses into a labelled upper step that records the lower nodes it covers. What matches nothing stays a generic step closed by the existing closing rules, the honest goto. Why it fits: each decision is local, deterministic and anchored; coverage comes from the closing rules, so the library never has to force progress; Phoenix's semantic-preservation lesson is the same test the specification uses for a level. Risk: it can miss intents silently, so the resolution report should count unmatched steps per level.
2. **Near-misses as declared broken variants (rules with negative application conditions).** Each pattern ships with the variants that are findings, such as "claim without guard", each an exact match naming the missing element. Why it fits: exact, deterministic, anchored to the element, explainable, cheap when anchored at the closing node; it generalizes the existing atomicity check; SAILR's goto-guided search suggests trying near-miss rules only around moves with a non-atomic verdict. Engler-style statistical deviance (one unguarded write among many guarded ones) is a later, optional addition, labelled as a prediction.
3. **Patterns per pack, compiler-aware in SAILR's sense.** A pack states the code shapes its library produces for one intent (an ORM's filtered update, `select_for_update`, a Redis `SET NX`), and the matcher inverts them. Why it fits: packs already carry the semantics of libraries, and SAILR shows that knowing how code was produced beats both a generic pattern set and pattern-free structuring. Risk: the `andn` problem, where each intent has many minimal forms. Generating the variants from the pack's semantics, as the CGO 2018 paper synthesizes rules, is the remedy, but that is a research step.
4. **Critical pair analysis and layering as a check on the pattern library.** Run when a pack or the library changes, not on each build. Two patterns that can claim the same node without a NAC separating them fail the check, with both names. One layer per level gives termination for free. Why it fits: "several patterns match" becomes a library error instead of a runtime tie-break, the only treatment of ambiguity consistent with fail rather than degrade. Implement it for mentalc's restricted rule language; do not depend on AGG, GROOVE or GrGen (Java/.NET, and too general).
5. **Reaching conditions (Dream) as a computation, not as a structurer.** For a write, the boolean condition under which it runs, built from the guarded edges from the behavior's entry, tells whether the write is conditional on what was read. That is the input to a move's verdict, and to a pattern's "write guarded by test of `s`". It is pure and deterministic; the risk is condition blow-up on large behaviors (the SoK's practicality complaint), bounded here because moves are small.
6. **Generic closing rules alone, the pattern-independent baseline.** They already fit: complete, deterministic, no library to maintain. Dream versus SAILR suggests that alone they give complete but unnamed and less faithful upper levels, and no near-miss findings. Keep them as the base under rank 1, not as the whole answer.
7. **Cost-based tiling with dynamic programming (BURS, iburg).** Deterministic and optimal for trees, but it settles semantic ambiguity by hidden costs, it is tree-only, and DAG covering is NP-complete. Use it at most for choosing among readings that are equivalent at different grain, inside a known region. A semantic choice should be decided by the library check in rank 4.
8. **Graph edit distance and error-tolerant matching.** Good as a metric: region-decomposed distance from mentalc's ladder to a hand-built reference ladder, as SAILR measures closeness to source. Poor as a finding mechanism: NP-hard, cost-dependent, unstable approximations, and no named missing element unless the edit script is kept.
9. **Goto-free forcing (Dream's restructuring transformations, rev.ng's duplication).** It does not fit. It invents structure (structuring variables, duplicated conditions or nodes) that the code does not contain, which breaks anchoring, and SAILR measured it as the least faithful option.

Not checked: Sharir 1980, Allen 1970, Cifuentes 1994, the iburg paper text, Dream's loop-structuring pages and the graph transformation textbooks were not read this session, so their details are [B] or [S]. The transfer of every decompiler result to effect graphs is inference; no source studies lifting service-level effect graphs.
