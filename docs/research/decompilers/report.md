# Patterns Name Steps, Closing Rules Cut Them

The decompiler toolbox splits cleanly for `mentalc`. The parts that fit are the deterministic ones: stored intermediate languages (ILs) per level with a declared contract, condition-aware pattern matching with an explicit residue, idiom tables supplied per library, and a per-build check of each lifted level against the level below. The parts that do not fit are the ones that guess: similarity scores, probabilistic recovery, structure forced onto code that has none, and LLMs that write structure. The owner's idea is therefore sound as a lifter, with one correction to its framing: **no decompiler reports "almost an idiom" as a defect**. The near-miss finding has to be borrowed from protocol state-machine checking and bug-pattern detectors, where a small pattern describing the broken shape is matched exactly and each hit stays a prediction until a run confirms it. Against the current design the two are less rivals than halves: closing rules decide where a step ends and guarantee that every lower step is covered, while patterns say what a step is and what it lacks. Decompiler history (Dream against SAILR) suggests that cutting without a library gives complete but unnamed levels, and a library without a covering base misses silently. Nothing here is measured on Mental: `mentalc` builds neither design yet, the closing rules have been measured only in a research harness, and the pattern design has not been run at all. The first experiment recommended is the cheapest one that measures both sides on the same code: five move-level patterns with declared broken variants, laid over moves cut by the closing rules, on report-jobs and rq.

## What the two designs are, on one claim

The running example is the claim in `generate_report`: read the row, test that its status is `PENDING`, write `RUNNING`, with no conditional update. Two activations of the task can both read before either writes, and the report is processed twice.

**The current design** cuts this by a rule stated over properties the model already has. A move closes at a write to shared state, so the read, the test and the write are one move. Its verdict comes from its own reads and writes: it reads, decides in the program and writes unconditionally, so it is non-atomic. A static check then reports a non-atomic move on a state variable that another activation can write. Above the move, an activation closes when the entity must wait, a goal when the actor's request is answered, an outcome when the subject reaches a terminal state. Every step class is identified by code names, the LLM names it afterwards, and a pair check runs the lower level and compares its projection with the upper steps. The rules need no library, cut every step, and say nothing about what a step is for: the move is "the steps up to this write".

**The pattern design** gives each level an instruction set and a library of patterns over the level below. "Claim" would be: read state variable `s`, branch on `s` having one value, write `s` to another value, with evidence on the write that the store itself enforces the test. A match compiles the three effect nodes into one `claim` instruction of the move-level IL. The example matches every part except the evidence, and that partial match, anchored at the write, is the duplicate-claim finding with the missing element named.

The honest comparison on this one example is that **both designs find the bug**. The current atomicity check already behaves like one near-miss rule, as the structuring note observes. What the pattern design adds is the name of the intent, a statement of which element is missing, and a route to bugs the atomicity check does not express: a message sent before the commit that makes its row exist, an outbox write outside the transaction, a consumer with no key check under at-least-once delivery. What it costs is a library that must be written, kept unambiguous and kept complete. Whether the addition outweighs the cost is the open question, and it is a measurement, not an argument.

## Deterministic lifting transfers almost whole

### An IL per level is how the mature decompilers are built

The owner's idea of one IL per level has direct precedent. Binary Ninja stores each level as its own IL with its own instruction indices and static-single-assignment form, and links instructions across levels many-to-many, warning that "you can not rely on an instruction from one layer existing in another" ([LLIL docs](https://docs.binary.ninja/dev/bnil-llil.html)). Each level removes one kind of detail: flags, then registers and the stack, then unstructured control flow ([BNIL overview](https://docs.binary.ninja/dev/bnil-overview.html)). Ghidra shows the alternative, one mutable graph whose phases are held in order by code comments ([coreaction.cc](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Features/Decompiler/src/decompile/cpp/coreaction.cc)). Mental's records are written, not edited, so the stored-level form is the one that fits.

Three contracts from this lineage are worth copying, because each turns an implicit ordering into something checkable. MLIR lets a conversion declare which operations are legal at the target level, legal under a condition, or illegal, and offers a full mode that fails unless only legal operations remain and an analysis mode that computes what would convert and applies nothing ([MLIR Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)). That is Mental's coverage check, stated as a property of the level and not of the lifter. Hex-Rays' maturity levels are promises about which facts hold at each point, and a client can ask for microcode only up to a chosen level [search]; its plug-in rules fire at every maturity, so authors must "write our patterns targeting the lowest maturity level at which we can reasonably match them" ([Rolles on the microcode API](https://hex-rays.com/blog/hex-rays-microcode-api-vs-obfuscating-compiler)), which is the fragility a pattern that declares its level avoids. angr makes that declaration a class attribute on every pass ([angr optimization passes](https://docs.angr.io/en/latest/api/angr.analyses.decompiler.optimization_passes.html)).

On traceability the notes find that Mental already plans more than decompilers keep. Every system keeps an address on each IL instruction, but none stores a validated map of which lower steps make up each upper construct. angr's practical rule is to copy the graph "before the first structure-altering optimization pass; use it for an exact instruction-to-AIL mapping" ([angr Clinic docs](https://docs.angr.io/en/latest/api/angr.analyses.decompiler.clinic.html)): build the step map at the moment a step is cut.

### Patterns must match evidence, and the residue must stay visible

Phoenix supplies the most important single lesson for a pattern library. Classical structural analysis matched shape only, and its natural-loop schema collapsed a loop with two exits into a node from which "both exit edges can be taken", correct for reachability and wrong for behavior. Phoenix made schemas "match both shape and the boolean predicates that guard execution of each node", and that change alone raised the number of coreutils programs whose decompiled form passes the full test suite **from 46 to 60 of 107** ([Phoenix](https://www.usenix.org/system/files/conference/usenixsecurity13/sec13-paper_schwartz.pdf)). A move pattern that matched read, branch, write by shape would label the buggy claim "claim" and hide the bug. The pattern has to match the guard, the lock or the transaction, which is the test the specification already applies to a level: a step may stand for the steps beneath it when nothing those steps do can change what is seen at its own level.

The second lesson is about what to do when nothing matches. Dream removed the pattern library, computed each node's reaching condition and reached zero gotos; rev.ng reached zero by duplicating code. SAILR then measured closeness to the original source on 7,355 functions: pattern matching with gotos sits at a mean control-flow edit distance of **about 22.5** (SAILR 22.64, Hex-Rays 22.52, Phoenix 22.64), while the goto-free methods sit at **45.99 (Dream) and 71.29 (rev.ng)**, with Dream emitting 43,661 boolean expressions against 6,180 in the source ([SAILR](https://www.usenix.org/system/files/usenixsecurity24-basque.pdf)). Forcing everything into the vocabulary costs faithfulness. The same paper states the limit of libraries: "there are more graph schemas in real-world binaries than one can reasonably enumerate". Every decompiler therefore keeps an explicit marker for what it could not raise: Binary Ninja's unimplemented and intrinsic instructions, remill's memory intrinsics ([remill INTRINSICS.md](https://github.com/lifting-bits/remill/blob/master/docs/INTRINSICS.md)), the goto. For `mentalc` the marker is a step that no pattern names, kept as a first-class kind and counted. Ghidra's habit of capping a loop and warning (type propagation stops after seven passes, "This constant arrived at empirically") is the opposite of failing rather than degrading and should not be copied.

Silent misses are the specific risk of a library. Instruction selection, the same problem run forwards, found that one x86 instruction has four minimal IR patterns and that "if a pattern is missing, the instruction selector cannot generate the corresponding instruction"; synthesizing rules from formal semantics found **31,612 rules missing in GCC and 36,365 in Clang** ([Buchwald, Fried, Hack](https://i44vm2.informatik.kit.edu/uploads/publikationen/buchwald18cgo.pdf)). "Claim a job" will have several forms across ORMs, drivers and queues: a filtered update, a row lock followed by a write, a set-if-absent in Redis. A library that lacks one does not fail; the step stays unnamed and no finding is made. The remedy the notes propose is a count of unmatched steps per level in the resolution report, beside the count of unresolved sites that exists today.

### Why this could work where plan recognition stalled

The closest prior art is not a decompiler. GRASPR represented programs as attributed flow graphs and clichés as a graph grammar, and produced "hierarchical design descriptions" by chart parsing ([GRASPR](https://sites.cc.gatech.edu/reverse/graspr.html)). The idioms note's account of why the line stalled is from training knowledge and should be read as such: hand-built libraries stayed small, subgraph matching is exponential in the worst case, one plan has many implementations spread across a program, and nobody measured recall on real code [training]. Its inference is that `mentalc` removes part of this before matching starts. Behaviors are small, one per provided port, and packs have already turned library calls into a few effect kinds, so an ORM query and a raw `SELECT` are both a read of one store. Decompiler idioms work because they come from a closed source, what a compiler emits; packs are the nearest thing Mental has to that closure, and SAILR's "invert what GCC does" maps onto a pack stating the shapes its library produces for one intent. The library cost remains, and whether pack normalization leaves few enough forms per intent is unmeasured.

## The near-miss finding comes from outside decompilers

Decompilers apply an idiom or leave the lower form. The nearest decompiler precedents are a warning that a jump table could not be recovered [training], Phoenix's "switch candidate" (a region "that would match a switch schema … but contain extra edges", repaired rather than reported), and the residual goto, for which the verification note found no source that says how often it points at a real defect. The owner's finding needs a different lineage, and the notes offer three mechanisms that disagree on how a near-miss is defined.

**Declared broken variants** are the first. Each pattern ships with the variants that are findings, written as the same left-hand side with a negative condition: claim, with no guard evidence on the write. Matching the variant is an exact match, so the result is deterministic, anchored to the element and explainable. The best evidence for this form is in protocol analysis. Fiterau-Brostean and colleagues define a bug pattern as "a (typically small) automaton specifying a particular error in an implementation's control logic, for instance sending two specific messages in the wrong order, or omitting an authentication step", intersect each with the system's model, and turn every hit into a test "to find a witness for the bug or filter out false alarms". On three SSH servers and nine DTLS implementations this reproduced all previously reported bugs and found new ones, and **many small named patterns beat one large automaton of allowed behavior**, which failed to produce witnesses for all bugs after a day ([NDSS 2023](https://www.ndss-symposium.org/wp-content/uploads/2023-68-paper.pdf)). Their model is learned and possibly wrong; Mental's is compiled, and `mentalvm` plays the part of the test on the real implementation.

**Constraint relaxation** is the second: match the full pattern, and on failure find the smallest set of constraints whose removal gives a match, reporting the removed ones. The idioms note attributes this to DeMIMA's "distorted" micro-architectures, from training knowledge only [training]. It finds near-misses nobody declared, at the price of a search and a ranking rule. **Alignment** is the third, from process-mining conformance checking: pair a path with a pattern using synchronous moves, moves only the path makes and moves only the pattern requires, so that a missing guard is one pattern-only move with a cost [training]. Graph edit distance generalizes this and the structuring note rejects it as a finding mechanism: it is NP-hard, depends on edit costs nobody can justify, and SAILR found exact distance "usually too expensive to run on graphs with more than 12 nodes".

The recommendation is to start with declared variants and keep relaxation beside it as the competing design, because the first is the only one of the three whose evidence was read in a primary source and the only one with no tuning parameter. What decides precision in every working detector is a gate on intent. ACIDRain found that **17 of 22** attacks on 12 e-commerce applications were caused by transaction scope in application code rather than by the isolation level, and needed about two hours of manual work to confirm each one ([The Morning Paper on ACIDRain](https://blog.acolyer.org/2017/08/07/acidrain-concurrency-related-attacks-on-database-backed-web-applications/), a secondary source). The idioms note adds, from training knowledge, that RacerD and FindBugs report only where the code's own locking shows it meant to be safe [training]. For `mentalc` the gate is concrete: a read that tests a status column followed by a write of that column, in a port that can be activated twice at once, is a claim attempt; a read followed by any write is not. SAILR's search, confined to "the blocks around a goto edge", suggests confining near-miss rules to moves whose verdict is already non-atomic. Each hit stays a prediction until `mentalvm` produces a witness, as static findings are labelled today. The false-alarm rate of near-miss reports in a system model is unmeasured anywhere in the notes.

Ambiguity gets the same treatment. Decompilers settle it by fixed preference (Phoenix reduces "the loop with the smallest loop body" first; Ghidra runs a fixed rule order) and report nothing. Library recognizers refuse: FLIRT's stated policy is "It is better not to recognize than to recognize wrongly" ([FLIRT in depth](https://docs.hex-rays.com/core/flirt/concepts/ida-f.l.i.r.t.-technology-in-depth.md)), and WARP dropped matches when a larger dataset produced "collisions on functions which previously had none" ([WARP](https://binary.ninja/2025/08/22/warp.html)). Graph-transformation theory offers the stronger form: critical pair analysis overlaps the left-hand sides of every pair of rules "in all possible ways" and "represents precisely all potential conflicts" ([AGG](https://user.tu-berlin.de/o.runge/AGG/WWW/critical_pairs.html)). Run when the library or a pack changes, it turns "two patterns can claim the same write" into a library error naming both, and one layer of rules per level gives termination because no rule consumes what it produces.

## Techniques that do not fit, and the verification that does

**LLMs must not lift.** On real functions from fuzzing targets, Hex-Rays reaches a coverage-equivalence rate of 0.418 against 0.346 for the best general LLM and 0.164 for LLM4Decompile, and letting an LLM rewrite Hex-Rays' output lowered coverage equivalence by **17.2 to 52.2%** while an LLM-based tool scored 1581 for understandability against Hex-Rays' 1162 ([DecompileBench](https://arxiv.org/html/2505.11340v1)). Output gets easier to read exactly where it gets less correct. A 2026 control study found that an LLM's naming gain did not change when the input's dataflow was destroyed (+0.001), with readability at ceiling throughout, so "a reader is given no signal" ([memorization floor, abstract only](https://arxiv.org/abs/2609.17236)). Every commercial integration the note found has the LLM drive or annotate a deterministic decompiler, never replace its structuring [training, plus vendor pages]. This confirms Mental's existing split and adds one usable control: ask for a name with the code's identifiers removed, leaving only what the step reads, writes and decides, and see whether the name survives.

**Scores and probabilities do not make facts.** Fuzzy function similarity, probabilistic variable recovery, cost-based tiling and statistical deviance ("nine of ten writes to this column are guarded") all produce a ranking. The notes agree that such output can order candidates or label a prediction and can never create or remove a record.

**Learning from runs is the wrong problem.** Protocol reverse engineering generalizes from positive examples, and Prospex cites the limit directly: "a regular language cannot be learned from positive examples only" ([Prospex](https://sites.cs.ucsb.edu/~chris/research/doc/oakland09_prospex.pdf)). `mentalc` has the code, so lifting is matching and abstraction, not learning. Active automata learning needs a running system; with `mentalvm` as the oracle it becomes a method for the planned comparison of statically derived step classes against explored runs.

**Verification transfers, and makes the pattern library cheap to trust.** The pair check is translation validation: each lifted level is checked against its own lower level on every build, so a pattern needs no proof of its own, only a failing check when it is wrong. Two additions come from decompiler testing. D-Helix compares a function with its recompiled decompilation symbolically and then toggles decompiler heuristics one at a time to find the one at fault, locating the cause for 7 of 17 new bugs [search] ([D-Helix](https://www.usenix.org/conference/usenixsecurity24/presentation/zou)); with patterns as configurable rules, a failed pair check can be rerun with one pattern disabled at a time. Equivalence-modulo-inputs testing found decompiler bugs by feeding programs that must decompile alike [search] ([Liu and Wang](https://monkbai.github.io/publication/2020-issta-decompiler-testing)); the analogue mutates a repository in ways that must not change the upper model, and in ways that must.

## What should be tried first

The two designs answer different questions, and the levels differ in how well a pattern can answer them. At the move level a pattern has something to say that a closing rule cannot, and the database studies place the bugs there. At the goal and outcome levels a step ends when a request is answered or a subject reaches a terminal state, which are properties, not shapes; catalog patterns that span two behaviors, such as an outbox, would sit at the activation or goal level and need lower patterns already matched. The earlier rq measurement found every symptom at the outcome or goal level and most causes at the move or activation level, which is where a near-miss would be anchored.

Three designs are therefore worth keeping side by side. In the first, the current one, closing rules cut and nothing is named mechanically. In the second, a hybrid, closing rules cut and guarantee coverage while patterns label the cut steps and report declared near-misses; because the base always covers, patterns can be strict and never need Phoenix's last-resort refinement. In the third, the owner's idea in full, patterns do the cutting and compile into a per-level IL, with a residue instruction for what matches nothing. No finding separates them yet. Comparing them requires both sides built on the same subjects, with the same counts taken from each.

| 8 | Name ablation | step names are requested with identifiers removed, footprint kept; the share of names that survive is reported beside the name-truth pass rate | the naming task |

**Experiment 1 comes first.** It is the smallest piece that puts both designs on the same code, since the rule-cut moves and the static checks are the baseline the patterns are laid over. It answers the three things no source can: how many moves a small library leaves unnamed, whether patterns find anything the existing checks do not, and how many near-misses are noise. If five patterns name few moves or add no finding on two subjects, the full IL design is not worth its library; if they add findings the checks cannot express, experiments 3 and 4 say how far up the ladder the idea reaches. Reasonable defaults for the prototype, all open to change: patterns declare the level they read; a pattern that strictly contains another's constraints wins and any other overlap is a library error; an unnamed step is a visible kind with a count; a pattern's name comes from the library while the step class keeps its identity from code names.

## Conclusion

The decompiler analogy holds for lifting and breaks for findings. Lifting by exact, evidence-aware patterns into stored ILs with a declared contract and a visible residue is standard, deterministic and compatible with every principle the specification sets. Reporting what almost matched is not something decompilers do; it is what bug-pattern automata and intent-gated detectors do, and their discipline (a small declared pattern of the broken shape, an exact match, a witness before the claim) is already how Mental labels static findings. That reframes the owner's idea: the valuable artifact is less the IL than the library of intents with their named failure modes, a machine-checkable version of catalogs that today exist only as prose and that no source in the notes has formalized over code.

The choice between pattern lifting and closing rules should stay open, and probably ends as neither alone. Decompilers that only cut produce output that is complete and unlike the source; decompilers that only match leave gotos where the library ends. The measurement that matters is on Mental's own subjects: the share of steps a small library names, and the findings it adds beyond the checks that already exist. Two risks carry through every experiment. A pattern library tuned to report-jobs and rq says little about a third system, and every near-miss count is a count of predictions until `mentalvm` can confirm them.
