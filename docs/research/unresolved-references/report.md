## Per-product summary

IDEs and language servers:

- **IntelliJ IDEA + Gradle**: runs the real build's configuration phase through the Tooling API; all-or-nothing on failure until Gradle 9.7 + IDEA 2026.2 "resilient sync".
- **IntelliJ IDEA + Maven**: own importer reads POMs with a chosen JDK; generated sources found by folder convention or by running Maven to a chosen phase.
- **JetBrains Bazel plugin**: runs Bazel aspects plus `bazel query` (snippet-only).
- **CLion / clangd**: need a per-file compile command; with none, clangd falls back to `clang foo.cc` and guesses header commands by filename.
- **PyCharm / pyright**: need an interpreter with dependencies installed; pyright keeps going and types the holes as `Unknown`.
- **gopls**: `go list` through `go/packages`; near zero-config since v0.15; returns partial results with per-package errors.
- **rust-analyzer**: runs `build.rs` and proc macros by default; non-Cargo builds supply `rust-project.json`.
- **tsserver**: `tsconfig.json` or an inferred project for loose files; needs `node_modules`.
- **Eclipse JDT LS**: embeds m2e and Buildship; needs Java 25 to run, separate from the project JDK.
- **Roslyn / Visual Studio**: MSBuild design-time build evaluates and resolves without compiling; on failure, a warning and incomplete IntelliSense.
- **Metals / BSP**: exports the build to Bloop or talks BSP; BSP is JVM/Scala-centred, not a universal interchange.
- **Kotlin LSP (official)**: alpha; Gradle and Maven JVM import, no multiplatform yet.

Indexers and analysers:

- **CodeQL**: `build-mode: none` by default for Java, C#, C/C++, Rust; asks Maven/Gradle for dependencies without compiling, guesses from package names otherwise, loses generated code; Kotlin, Go and Swift still need a build.
- **SCIP / Sourcegraph**: indexers run on top of the real compiler or type checker; external symbols get an identity (manager, package, version, path); failed or absent index falls back silently to search-based navigation.
- **Kythe / Glean**: record each real compiler invocation; no degraded mode for code that does not compile (Kythe details snippet-only).
- **GitHub stack graphs**: precise build-free name resolution from per-file scope graphs; repository archived 9 September 2025 (snippet-only).
- **Joern**: fuzzy parsing without a build; can fetch jars for type information only; invents dummy types for unresolved receivers.
- **Semgrep**: CE is single-file; Pro adds cross-file analysis with documented gaps and a fallback to single-file (snippet-only).

Agent-oriented tools:

- **Aider, Potpie, Greptile**: tree-sitter or graph extraction with identifier-name matching; no resolution statistics (Aider snippet-only; tree-sitter use by Potpie and Greptile unverified).
- **Cursor**: embeddings over chunks; semantic search, no reference graph.
- **Serena, Claude Code LSP plugins, JetBrains MCP server**: delegate to a language server or the IDE engine; precise only when the user's environment is set up (snippet-only).

Dependency-graph tools:

- **Syft, Trivy, OSV-Scanner**: lockfile and manifest parsers; exact on a lockfile, weak without one; Trivy and OSV-Scanner re-resolve Maven with their own resolvers.
- **cdxgen**: the one generic tool that invokes Maven, Gradle and pip; more complete, needs toolchains and executes project code.
- **deps.dev**: resolves published package versions on public registries only; cannot resolve a local manifest, private packages or through git dependencies.
- **GitHub dependency graph**: static parsing plus build-tool submission that runs in Actions; not usable locally.

## Summary

Unresolved references are the normal state of static analysis, and projects do not reliably build from source without a human. **38% of about 7,200 GitHub Java projects failed their default build in 2016, 59% in a 2020 replication**, with dependency resolution the leading cause; the best-resourced tools have responded by giving up on the build instead of fixing it (CodeQL now defaults to no-build extraction for Java, C#, C/C++ and Rust, and reports **over 70% unattended success on more than 10,000 C/C++ repositories**). Every precise tool (JetBrains IDEs, language servers, SCIP indexers, Kythe) gets its precision by running the build tool or compiler, which executes repository code and needs a human for trust, toolchain, credentials and generated sources. Every build-free tool (Semgrep CE, Joern, tree-sitter code graphs for agents) resolves by name or guesses types, and none publishes how many references it failed to resolve. The existing toolset pins the whole dependency graph only where a lockfile is on by default (the npm family, Cargo, Bundler, Composer, SwiftPM, uv/Poetry/PDM) or where the manifest is deterministic (Go); for Maven, Gradle, NuGet without a lock and unpinned Python the exact graph exists only after running the native resolver, and SNAPSHOTs and branch references identify content only at the moment of resolution. For Mental the dangerous loss is not a missing call edge but a silently missing port, effect or state write site, because nothing downstream knows it is absent. The recommendation is a ladder that never executes repository code by default (lockfile, then the developer's existing caches, then pinned download, then agent-proposed resolutions that `mentalc` verifies), plus a build gate that fails on unresolved references at model-changing locations and carries the rest as counted, typed facts. That squares with "fail rather than degrade": what the principle forbids is a silent gap, not an accounted one.

Evidence labels used throughout: a citation with no label was read in full by the researchers; **snippet-only** means the claim comes from a search-result summary of the linked page and is a lead, not a confirmed fact; **unverified** means it rests on prior knowledge or secondary reporting and was not checked this session.

## Half of arbitrary repositories do not build unattended

The claim that projects nowadays build from source without human involvement does not survive the evidence for the JVM, and nobody has measured it for most other ecosystems. Sulír and Porubän built 7,264 GitHub Java projects with their default command in 2016: **38.05% failed, and dependency errors were the largest category at 39.2% of failures** ([arXiv 1712.01024](https://ar5iv.labs.arxiv.org/html/1712.01024)). A 2020 replication on JDK 11 put the failure share at **59%** ([arXiv 2408.11544](https://ar5iv.labs.arxiv.org/html/2408.11544)). Later figures point the same way but are leads only: about half of the top 200 Java projects failing with default commands in 2017, with inconsistent exact counts across summaries ([Hassan et al.](https://foyzulhassan.github.io/files/ESEM17_Full_Paper.pdf), snippet-only), and a 2026 study reporting 30 to 44% failure across JDK versions ([Springer](https://link.springer.com/article/10.1007/s10664-026-10806-6), snippet-only, page not readable). Buildability also decays: one study found that on average only 38% of a project's change history still compiles ([Tufano et al.](https://microsoft.com/en-us/research/?p=771955), snippet-only), so any extraction of history has to be build-free.

The strongest current number comes from GitHub. When CodeQL's build-free C/C++ mode went generally available in October 2025, GitHub reported more than 10,000 repositories enabled "with a success rate above 70%" and no manual intervention ([GitHub changelog 2025-10-14](https://github.blog/changelog/2025-10-14-codeql-scanning-rust-and-c-c-without-builds-is-now-generally-available)). That figure measures "scan completed", not accuracy, and it is the success rate of the mode designed to avoid the build. GitHub's own comparison table rates unattended success as "Yes" for `none`, "Variable" for `autobuild` and "No" for `manual` ([GitHub Docs](https://docs.github.com/en/code-security/code-scanning/creating-an-advanced-setup-for-code-scanning/codeql-code-scanning-for-compiled-languages)).

LLM agents have not closed the gap. ExecutionAgent ran test suites for 33 of 50 projects at an average of **74 minutes** per project ([arXiv 2412.10133](https://arxiv.org/abs/2412.10133)); Repo2Run built environments for 361 of 420 Python repositories, 86.0% ([arXiv 2502.13681](https://arxiv.org/html/2502.13681v3)). On benchmarks chosen to be hard the rates collapse: EnvBench reports the best approach configuring 29.47% of JVM and 6.69% of Python repositories ([arXiv 2503.14443](https://arxiv.org/pdf/2503.14443), snippet-only), and SetupBench 38.9 to 57.4% ([arXiv 2507.09063](https://arxiv.org/abs/2507.09063v1), snippet-only). These benchmarks differ in scope and are not comparable with each other; all used 2024-era models.

Two caveats bound these numbers for Mental. A full build is a stricter bar than dependency resolution, so import failure sits below build failure by an unmeasured amount. And the studies sample cold checkouts of other people's repositories, the worst case; Mental's target, a team's own active repository on a developer machine with warm caches and credentials, is the best case. No public telemetry exists on IDE sync failure rates, and no study measures "opens with all references resolved and zero manual steps" for any IDE or language server.

Even a perfect build does not make the problem go away. Static call graphs built with everything available miss real calls: **recall of about 69.9% at 99.2% precision for PyCG on real Python projects** ([arXiv 2103.00587](https://arxiv.org/pdf/2103.00587)), median 0.884 for Java ([ICSE 2020](https://2020.icse-conferences.org/details/icse-2020-papers/47/On-the-Recall-of-Static-Call-Graph-Construction-in-Practice), snippet-only), and 75.9% rising to 88.1% for JavaScript with approximate interpretation ([Møller et al.](https://cs.au.dk/~amoeller/papers/approx), snippet-only). On a micro-benchmark PyCG is complete on 107 of 126 cases while Jelly on JavaScript is complete on 49 of 126 ([arXiv 2410.00603](https://arxiv.org/html/2410.00603v2)). Two kinds of gap therefore need separate treatment: a target that lies outside the analysed code, which is an identity problem, and a target inside the code that cannot be determined statically, which costs 10 to 30% of recall regardless of the build.

## Precise tools run the build; build-free tools guess

### JetBrains IDEs need a human in four places

JetBrains IDEs do not parse Gradle or Bazel build files; they run the build tool and ask it for a model. Gradle sync goes through the Tooling API, which always uses the daemon and can download the wrapper's Gradle version ([Gradle Tooling API](https://docs.gradle.org/current/userguide/tooling_api.html)), and fetching models requires configuring projects, build scripts, included builds and `buildSrc` ([Gradle blog](https://blog.gradle.org/resilient-sync)). The classpath is computed by code, so nothing short of executing that code yields it. Maven sits in the middle: the importer resolves dependencies from the POMs, but plugin-generated sources need either a folder-convention guess or a real phase run, and IDEA exposes both as settings ([IntelliJ help: Maven importing](https://www.jetbrains.com/help/idea/maven-importing.html)), which is evidence that neither is reliably right.

The human steps cluster into four kinds. **Consent**: in Safe Mode "no build scripts are executed and no dependencies are resolved" until the project is trusted ([IntelliJ help: Project security](https://www.jetbrains.com/help/idea/project-security.html)). **Toolchain**: the importer JDK for Maven, and in PyCharm at least one configured interpreter ([PyCharm help](https://www.jetbrains.com/help/pycharm/configuring-python-interpreter.html)). **Generated code**: the Maven phase and generated-sources policy above. **Credentials** for private repositories are commonly reported as an import failure cause, but no primary source was found this session (unverified). Each of the four is something a headless extractor also lacks.

The failure behaviour is the most telling finding. Until this year a single broken Gradle script left the IDE with no model at all, because "a throwing build action discards everything it had already collected". **Partial models on failure arrived only with Gradle 9.7 and IntelliJ IDEA 2026.2**, and no other Tooling API client has committed to adopting them ([Gradle blog](https://blog.gradle.org/resilient-sync)). Early user reports of slow imports and a sync error under resilient sync exist but are not confirmed by JetBrains ([Kotlin Slack archive](https://slack-chats.kotlinlang.org/t/34437464/anyone-else-having-issues-syncing-projects-in-intellij-2026-), snippet-only). Most existing repositories are not on Gradle 9.7, so they do not benefit.

### Language servers delegate to one build tool per ecosystem

Language servers with a single dominant tool come close to zero configuration, and they degrade by marking holes instead of guessing targets. gopls "will typically work when you open a Go file anywhere in your workspace" since v0.15, although it cannot guess user-defined build constraints ([gopls](https://go.dev/gopls/workspace)), and `go/packages` returns partial results with errors attached per package ([go/packages](https://pkg.go.dev/golang.org/x/tools/go/packages)). pyright types what it cannot infer as `Unknown` and can run with no environment if stubs and local files cover the imports ([pyright type inference](https://github.com/microsoft/pyright/blob/main/docs/type-inference.md), [import resolution](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)). tsserver gives a loose file an inferred project with default options ([TypeScript wiki](https://github.com/microsoft/TypeScript/wiki/Standalone-Server-(tsserver))).

The supposedly easy ecosystems still execute project code: rust-analyzer enables build scripts and proc macros by default ([rust-analyzer configuration](https://rust-analyzer.github.io/book/configuration.html)), so an extractor that refuses to execute code misses everything proc-macro-generated. The hard ecosystems need an artefact only a real build produces: clangd without a compilation database falls back to `clang foo.cc`, and for headers picks "some entry whose filename most closely matches", a heuristic that "occasionally goes wrong" ([clangd design](https://clangd.llvm.org/design/compile-commands)). There is no cross-ecosystem hand-off format. BSP is real but JVM-centred ([BSP implementations](https://build-server-protocol.github.io/docs/overview/implementations)), and only `compile_commands.json` and `rust-project.json` are plain files produced once and consumed later. The realistic goal is "without compiling", not "without the build tool".

### CodeQL chose coverage over the build, and says what it loses

CodeQL is the closest precedent for Mental's extractor. Its Java no-build mode "will attempt to run Gradle or Maven to extract accurate dependency information (but not to invoke a build)"; when the build scripts cannot be queried it guesses dependencies from Java package names and says those guesses can be inaccurate. Generated code is not analysed, one version of each dependency is chosen, and colliding class names cause missing call targets. C# restores NuGet packages and generates a few source files; C/C++ infers compilation units, flags and include paths; Rust uses rust-analyzer to run build scripts and macros. **Kotlin, Go and Swift still require a build**, which marks where build-free resolution is hardest ([GitHub Docs: build options](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages)).

GitHub grades accuracy only as "Good" for `none` against "Best" for `manual` and publishes no precision or recall comparison. Two details about how CodeQL represents the gaps would matter to Mental if confirmed: unresolved callees are kept as expressions of an `ErrorType` that propagates, and a warning fires when 5% of expressions lack a type or 5% of call targets are unknown. Both come from a changelog mirror seen only as a search summary ([CodeQL Java changelog mirror](https://source-hub.etos-pro.ru/github/codeql/src/commit/addef2f1713ed270a56855304e46599e2c2b9d03/java/ql/lib/CHANGELOG.md), snippet-only) and need checking against the official changelog before the spec cites them.

### SCIP names external symbols; Kythe records the compiler

SCIP indexers are compiler-accurate because they run inside or on top of the compiler: scip-java is a compiler plugin, scip-clang needs a compilation database, scip-python reads the active environment ([scip-java](https://sourcegraph.github.io/scip-java/docs/getting-started.html), [scip-clang](https://github.com/sourcegraph/scip-clang), [scip-python](https://github.com/codean-io/scip-python), all snippet-only). Sourcegraph falls back to search-based navigation when no precise index exists and recommends running indexers in the customer's CI for "complex or authenticated builds" ([Sourcegraph Docs](https://sourcegraph.com/docs/code-navigation/precise-code-navigation)). The search-based tier is a ctags symbol search plus a word-bounded text search ([Sourcegraph Docs](https://sourcegraph.com/docs/code-navigation/search-based-code-navigation)), so it conflates same-named symbols.

The part worth borrowing is the symbol format. A SCIP symbol embeds `<manager> <package-name> <version>` and a descriptor path, and the index lists `external_symbols` "referenced from this index but ... defined in an external package" ([scip.proto](https://github.com/sourcegraph/scip/blob/main/scip.proto)). An external reference is thus resolved to an identity without the target's source being indexed. That works only because the indexer had the dependency's type information at index time.

Kythe and Glean sit at the far end: they capture each real compiler invocation (Kythe through a Bazel extra action, snippet-only via [pkg.go.dev](https://beta.pkg.go.dev/kythe.io@v0.0.67/kythe/go/extractors/bazel)), Glean indexes centrally on a shared fleet ([Engineering at Meta](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)), and neither offers a mode for code that does not compile. Both presuppose an organisation that controls its build.

### Build-free and agent tools resolve by name and publish no error rate

Joern is the nearest prior art to a build-free extractor. Its Java frontend has `--fetch-dependencies` ("Attempts to fetch dependencies jars for extra type information"), `--inference-jar-paths`, a delombok mode, and a type-propagation pass that generates dummy types; skipping type inference makes results "much worse" ([Joern Docs: Java frontend](https://docs.joern.io/frontends/java/)). Semgrep CE stops at the file boundary and Pro's cross-file analysis has documented gaps such as certain CommonJS exports ([Semgrep Docs](https://semgrep.dev/docs/semgrep-code/semgrep-pro-engine-intro), snippet-only). GitHub's stack graphs, the most ambitious precise build-free resolver, analysed each file in isolation with no build configuration ([GitHub Blog](https://github.blog/open-source/introducing-stack-graphs)); the repository was archived on 9 September 2025 ([archived snapshot](https://web.archive.org/web/20260601045401/https:/github.com/github/stack-graphs), snippet-only), with no public reason given.

Agent-oriented tools fall into three groups. Aider's repo map ranks files from tree-sitter tags ([Agent Patterns](https://www.agentpatterns.ai/context-engineering/repository-map-pattern/), snippet-only), and Potpie and Greptile build repository graphs of calls and imports ([Potpie](https://github.com/potpie-ai/potpie), [Greptile Docs](https://greptile.com/docs/how-greptile-works/graph-based-codebase-context)); name matching links or conflates two methods called `save`, and library calls have no definition at all. Cursor embeds chunks and builds no reference graph ([Cursor Blog](https://cursor.com/blog/secure-codebase-indexing)). Serena, Claude Code's LSP plugins and the MCP server built into IntelliJ IDEA since 2025.2 delegate to a language server or the IDE ([Serena](https://glama.ai/mcp/servers/oraios/serena/tools/find_referencing_symbols), [IntelliJ help: MCP server](https://www.jetbrains.com/help/idea/2026.2/mcp-server.html), both snippet-only) and inherit its need for a working project. **No tool in any group reports the fraction of references it failed to resolve.** That absence is the opening for Mental.

## Lockfiles pin the graph; Maven, Gradle and loose Python do not

The existing toolset does not resolve the whole pinned graph across build tools. It reads it where the ecosystem already wrote it down, and has to run the native resolver everywhere else.

| Ecosystem | Exact graph from files alone? | What a static reader gets | Evidence |
|---|---|---|---|
| npm, pnpm, Yarn, Bun | Yes, lockfile by default | version, tarball URL, integrity hash, git commit SHA in `resolved` | [npm docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json); pnpm, Yarn, Bun formats unverified |
| Cargo | Yes | caret ranges frozen in `Cargo.lock`, exact commit for git dependencies | [Cargo docs](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html) |
| Go | Yes, no lockfile needed | minimal version selection is deterministic from `go.mod`; `go.sum` is integrity only | [Go Modules Reference](https://go.dev/ref/mod) |
| Python with `uv.lock`, `poetry.lock`, `pdm.lock`, `pylock.toml` | Yes | exact versions across platform markers | [uv docs](https://docs.astral.sh/uv/concepts/projects/layout/), [OSV-Scanner](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/) |
| Python with `requirements.txt` ranges | No | needs a resolver, network, and a result specific to one OS and Python version | [pip report](https://pip.pypa.io/en/stable/reference/installation-report/) |
| Maven | No native lockfile | version depends on the whole effective POM chain (parents, BOMs, nearest-wins mediation) | [Maven docs](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html); absence of a lockfile in Maven 4 is snippet-only |
| Gradle | No | locking is opt-in; the lockfile has versions but no edges and no hashes; the graph needs the build scripts to run | [Gradle docs](https://docs.gradle.org/current/userguide/dependency_locking.html), [cdxgen](https://raw.githubusercontent.com/CycloneDX/cdxgen/master/docs/PROJECT_TYPES.md), [Trivy](https://trivy.dev/latest/docs/coverage/language/java/) |
| NuGet | Only after restore | `project.assets.json` is the real graph and is not committed; `packages.lock.json` is opt-in (unverified) | [cdxgen](https://raw.githubusercontent.com/CycloneDX/cdxgen/master/docs/PROJECT_TYPES.md) |
| Bazel | Partly | `MODULE.bazel.lock` stores registry hashes and extension results, not a readable graph | [Bazel docs](https://bazel.build/external/lockfile) |
| Bundler, Composer, SwiftPM | Yes, lockfile by default with git revisions | formats not re-read this session (unverified); GitHub lists them as files that define all direct and indirect versions | [GitHub Docs](https://docs.github.com/en/code-security/reference/supply-chain-security/dependency-graph-supported-package-ecosystems) |

Published accuracy studies say the numbers measure input mode more than tool quality. Starting from the same lockfiles, **Syft and Trivy were 100% accurate on name and version across 2,414 repositories** ([arXiv 2511.20313](https://arxiv.org/html/2511.20313v2)). Without one, a 10,000-repository study measured Java recall of 36.9% for Syft, 54.9% for Trivy and 38.2% for GitHub's graph against **98.4% for the Microsoft SBOM Tool**, and Python version accuracy of 21.6 to 31.0% for GitHub, Trivy and Syft ([arXiv 2607.04614](https://arxiv.org/html/2607.04614)). In a Python-only study the best existing tool reached 17% precision while a tool built on pip's own resolver reached 81% ([arXiv 2409.06390](https://arxiv.org/html/2409.06390v1)). Reusing the native resolver is what produces accuracy. Generating a missing lockfile automatically is not a safe fallback either: it worked for 96.4% of Rust repositories but only **19.1% of Python** ones ([arXiv 2511.20313](https://arxiv.org/html/2511.20313v2)). These studies validate name and version only; nobody has measured the accuracy of edges or of git-sourced dependencies.

### Sliding versions resolve only at a moment in time

Where a default lockfile exists, the resolved value of a range or tag is recorded automatically. Where it does not, the answer depends on when and where resolution runs. Gradle locking pins dynamic versions such as `1.+` but "should not be used with changing versions such as `-SNAPSHOT`" ([Gradle docs](https://docs.gradle.org/current/userguide/dependency_locking.html)). A Maven SNAPSHOT resolves through repository metadata to a timestamped build and a range to the highest version available at that moment (unverified this session; [Maven POM reference](https://maven.apache.org/pom.html#Dependency_Version_Requirement_Specification)). Static tools visibly stumble here: Trivy uses an empty version when it cannot determine one and then misses that dependency's children ([Trivy](https://trivy.dev/latest/docs/coverage/language/java/)), and in one sample project Syft and Trivy found only the 5 exactly pinned dependencies out of 15 ([arXiv 2511.20313](https://arxiv.org/html/2511.20313v2)). Hosted resolvers do not help: deps.dev defines its graph as what installing "on a generic 64-bit Linux system" would produce now, not the project's historical resolution ([deps.dev API](https://docs.deps.dev/api/v3/)).

The practical consequence is a labelling rule. A graph read from a committed lockfile is declared; a graph obtained by resolving today is observed at a time, on one machine. SNAPSHOTs and Gradle changing modules are the only widespread case where even a recorded version string does not identify content, so a timestamped version or content hash is needed. A library repository with no lockfile has no single exact graph at all: the honest record is the constraints plus one sample resolution.

### Git-sourced dependencies are pinned wherever a lock exists

For git dependencies the commit is knowable offline whenever a lockfile exists. npm stores the git URL with the commit SHA ([npm docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json)); Cargo records the exact commit in `Cargo.lock` ([Cargo docs](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)); Go pseudo-versions encode commit time and hash in `go.mod`, and `replace` applies only in the main module ([Go Modules Reference](https://go.dev/ref/mod)); pip's report records the requested revision and resolved commit ([pip report](https://pip.pypa.io/en/stable/reference/installation-report/)). Git submodules store the exact commit as a gitlink readable without network (unverified this session; [gitsubmodules](https://git-scm.com/docs/gitsubmodules)).

GitHub Actions gained the same property this year. `.github/workflows/actions.lock` records, per action, the `ref` it was resolved from and the exact `commit` that runs, including actions used by actions; it does not pin reusable workflow calls ([GitHub Docs: workflow dependency lockfiles](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles)). Its general availability on 28 October 2026 is from a third-party report ([InfoQ](https://infoq.com/news/2026/11/github-actions-lockfiles-ga), snippet-only), so most repositories will not have one yet.

What is weak is the tooling around git sources, not the pinning. deps.dev covers only public registries and, for Go, only modules served by proxy.golang.org ([deps.dev API](https://docs.deps.dev/api/v3/)), so JitPack, private artefacts and git-only packages are outside it. A git dependency's own transitive dependencies are known only by fetching that commit and reading its manifest. Without a lock, a branch or tag reference (`@v4`, `branch =`, `git+https://...@main`) needs `git ls-remote` and changes over time.

### Private registries favour running on the developer's machine

Tools that re-resolve through public metadata lose private packages. OSV-Scanner's Maven resolution uses deps.dev by default and is disabled offline ([OSV-Scanner](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/)); GitHub's automatic submission for Python "doesn't support private packages" and reaching private Maven registries needs self-hosted runners ([GitHub Docs](https://docs.github.com/en/code-security/reference/supply-chain-security/automatic-dependency-submission)). Mental's local-first setting is an advantage here. A committed lockfile already contains the resolved private packages, so reading the pinned graph needs no credentials; and the developer's machine already holds the credentials and warm caches (`~/.m2`, the Gradle and Go module caches, `node_modules`, site-packages) that a hosted resolver cannot reach. Once a version is pinned, the API surface follows without a build: Go modules are source ([Go Modules Reference](https://go.dev/ref/mod)), npm lockfiles give a verifiable tarball URL ([npm docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json)), and JVM class files and .NET reference assemblies describe the full public API (unverified this session). The shares of packages that ship `-sources.jar`, `.d.ts` or `py.typed` were not found.

## Silent gaps in ports, effects and write sites are the real damage

Almost every structural record in Mental sits downstream of the extractor's `resolve` step. Entry points and provided ports exist only if a decorator or registration call resolves to a pack's type; effects only if a receiver's type resolves to a pack type; state variables and their write sites feed the lifecycle machines, the machine check and the atomicity check; compile units are compiled bottom-up along the call graph with callee summaries substituted (`/Users/vs/workspace/mental/docs/specification.md` §6.2, §6.2.1, §6.2.2, §7). The primitive is already right: every lookup returns `Resolved(id) | External(qualified_name) | Unresolved(Reason)` with a closed reason enum, and the rule is "No heuristic edges, no name-similarity matching, no 'most likely' type" (`/Users/vs/workspace/mental/docs/guidelines/extract.md`).

The worst failure is therefore a quiet one. An unresolved decorator means no provided port, hence no behaviour, hence no finding, and nothing downstream knows something is absent. A missing write site makes a lifecycle machine look cleaner than the code and hides exactly the races Mental exists to find. A missing call edge, by contrast, is visible and countable. External-only gaps also cascade: the type of anything returned by a library call is lost, and with it every method call on that value, overload selection among repository methods, and members inherited from library base classes, so `self.save()` on a subclass of a library class looks like `not_found`.

Mental's exposure is narrower than whole-program analysis, because it needs library symbols resolved only up to the pack's type rows, not to library source. The "external library unresolved" problem becomes `no_pack` or "receiver type not inferable". And framework wiring is not a resolution failure at all: injection, annotation routing and string-keyed messaging live in framework semantics, and every serious tool recovers them with declarative models. JackEE's framework-aware analysis achieved more than four times the completeness of conventional techniques on Java enterprise applications ([PLDI 2020](https://pldi20.sigplan.org/details/pldi-2020-papers/66/Static-Analysis-of-Enterprise-Applications-Haven-t-We-Solved-This-Problem-Yet-), snippet-only). That is the same idea as packs and slots, and the evidence says it is the largest single lever for framework code.

The reason enum splits three ways, and only one part is helped by fetching dependencies. `eval`, `dynamic_attr` and `dynamic_import` are unresolvable by construction and belong as explicit assumptions or stubs. `no_pack` and framework wiring are resolvable with a model. `not_found` because a dependency or stub is absent is resolvable with more input. The spec does not yet say which reasons are errors, which are diagnostics and which become assumptions, and it states both that "a build either produces a full model or fails" (`/Users/vs/workspace/mental/docs/specification.md` §3, §6.5) and that each `Unresolved` becomes a fact. That tension has to be settled.

## A ladder that executes nothing, a gate that fails loudly

### Where the missing type information comes from

Five sources compete. They are complementary rungs more than rivals, but the order and the cut-off are a design choice to test.

| Option | What it recovers | Cost and risk | What must be tested to choose |
|---|---|---|---|
| A. Packs only (today's design) | effects, slots, write sites for covered libraries | `no_pack` for everything else; hand-written rows | share of unresolved references by reason on real repositories; how much is `no_pack` against `not_found` |
| B. Lockfile plus the developer's caches, read as data | exact versions; API surface (signatures, stubs) from which type rows are generated mechanically | lockfile parsers per ecosystem keep changing (pnpm 12, Bun, `pylock.toml`); cache version must equal the lockfile version | how often the cache holds the locked version; how much the unresolved count falls; whether generated rows are deterministic |
| C. Download the pinned artefact by URL and hash | same as B when the cache is cold | network; private registries need credentials; no code runs if install scripts are skipped | cold-cache success rate; time per repository |
| D. Ask the native build tool for its model | the exact graph for Maven, Gradle, NuGet and unpinned Python; module boundaries and source sets | executes repository code for Gradle and often Maven; needs toolchains; breaks "nothing else installed" | which queries run no repository code (`go list`, `cargo metadata`, Maven without extensions: unverified); failure rate on the target repositories |
| E. Agent as resolver of last resort | a proposed target or type for one unresolved site, optionally found through the agent's language-server or IDE tools | hallucination; cost per site | acceptance rate under deterministic verification; false acceptances; cost per resolved reference |

The evidence favours B first. With a lockfile, generic tools are exact; reading files executes nothing; and the JavaScript ecosystem itself is moving to scripts off by default, with npm 12 reported to disable lifecycle scripts except for allow-listed packages ([The Register](https://theregister.com/devops/2026/06/10/github-pulls-pin-on-npms-auto-run-scripts/5253453), snippet-only, shipping unconfirmed). Option D is the only route to an exact graph for Gradle and Maven, and CodeQL takes it, but in GitHub's hosted runners, not on a developer machine; JetBrains states that building a Maven or Gradle project from the command line carries the same risks as importing it ([JetBrains blog](https://blog.jetbrains.com/idea/2021/03/intellij-idea-2020-3-3/), snippet-only).

For option E the literature draws a clear line. LLMs are strong at local type inference, **93.7% exact match for gpt-4o on a 860-annotation micro-benchmark**, and weak at whole call graphs, complete on 76 of 126 cases against PyCG's 107 ([arXiv 2410.00603](https://arxiv.org/html/2410.00603v2)). Partial-program inference without an LLM lands in the same band: PPA recovered 91.2% correct types with 2.7% erroneous ones ([PPA](https://www.sable.mcgill.ca/ppa/)). Good enough to propose, not good enough to assert; the remainder would be silent errors in write sites and effects. The defensible pattern is the one SemTaint uses, handing only the unresolved call edges to an LLM ([arXiv 2601.10865](https://arxiv.org/abs/2601.10865), snippet-only), with `mentalc` verifying each proposal: the target symbol exists at the stated anchor, name and arity match, the receiver type defines or inherits the method, and a proposed dependency appears in the lockfile with rows regenerated from the artefact, never from the agent's text. Agent-driven environment setup, at tens of minutes and 7 to 86% success, is a poor default step.

**Recommendation.** Run A, B and C by default, in that order, with no repository code executed. Offer E as a bounded task list over the remaining unresolved sites, storing accepted proposals with a distinct provenance and the ledger call. Keep D behind an explicit trust decision: when `mentalc` runs inside a coding agent, the agent's permission system is that trust prompt, so the agent can run the build tool and `mentalc` only verifies the effect by re-extracting. For external targets, adopt SCIP's shape for `External`: package manager, package name, pinned version and descriptor path, with the graph labelled declared or observed-at-time.

### What a partially resolved model is allowed to be

| Policy | Behaviour | Strength | Weakness | What must be tested |
|---|---|---|---|---|
| 1. Strict | any `Unresolved` fails the build | simplest reading of "full model or fails" | recall below 90% even with a full build means nearly every real repository fails | share of repositories with zero unresolved references |
| 2. Flat threshold | fail or warn above a share, as CodeQL is reported to do at 5% | one number, easy to explain | an unresolved logging call counts the same as an unresolved decorator on a handler | distribution of unresolved share per repository and per module |
| 3. Location-weighted gate | fail when an unresolved reference sits where it changes the model: a decorator on a function, a receiver in a handler that writes state, a callee on a path to a port | strict exactly where silence is dangerous | needs a definition of "model-changing" per record kind | share of unresolved references at such locations; whether the gate catches seeded gaps |
| 4. Always succeed with facts | record everything, never fail | maximal coverage | the model is later read as complete, the outcome the spec forbids | not recommended; included as the baseline other tools use |

**Recommendation: policy 3, with policy 2 as a secondary guard per module.** This is how it squares with "fail rather than degrade". The principle targets silent degradation: Sourcegraph's unannounced fallback to text search, PyCG returning with no record, a crippled fallback that looks like the real thing. It does not require a property no static analysis has. The reconciliation is to redefine "complete" from "every reference resolved" to **"every reference accounted for"**: each one is `Resolved`, `External` with an identity, or `Unresolved` with a reason, a recorded call shape, and a visible consequence. Three rules make that hold.

First, a missing input is an error, not a guess. When a locked package has no pack, no cached artefact and no stub, the build fails with a diagnostic naming the package, the version, the modules affected and the command that would supply it. CodeQL's fallback of guessing dependencies from package names is exactly the degrade-with-warning step Mental should not copy.

Second, an unresolved reference at a model-changing location fails the build unless it is explicitly accepted, and acceptance turns it into a recorded assumption: a `call` node wired to a stub with every declared outcome and provenance `assumed`, so the interpreter's existing "model gap" outcome and every downstream check see it. Nothing is left for another tool to fill; the gap is a first-class record with an owner.

Third, every unit carries its counts. Resolved, external and unresolved totals per function, compile unit and module, by reason, travel with the model, so no consumer can read a partial model as a whole one. Candidate targets found by name are stored as candidates for a later resolver, never as edges. And a hallucinated "this cannot be resolved, ignore it" is never accepted, consistent with Mental's own finding that LLM filtering loses confirmed bugs (`/Users/vs/workspace/mental/docs/findings.md`, F-R3).

One experiment decides most of this. Take a handful of real repositories across Python, TypeScript and a JVM build, run the extractor with packs only, and tabulate unresolved references by reason and by location. Then add rungs B, C and E one at a time and record the fall in the unresolved count, the time spent, and for E the verifier's acceptance and false-acceptance rates. Seed known gaps (remove a pack, break an import on a handler) and check that the gate fires. The same run yields the first published resolution-rate figures for an agent-facing code model.

## Conclusion

The survey changes the framing of the question. Unresolved references are not a defect of immature extractors that enough engineering removes; the industry's two largest code-analysis vendors both moved away from requiring the build, and the most precise IDE gained a partial-model story for Gradle only this year. The competitive question is no longer who resolves everything but who says truthfully what was not resolved, and on that nobody in the surveyed field publishes a number.

Mental's constraints, usually read as handicaps, line up with the evidence. Local-first means the lockfile, the caches and the credentials are already present, which is where accuracy comes from. Declarative packs mean library knowledge is needed only to the depth of type rows, which pinned artefacts can supply mechanically. And the coding agent supplies both the trust prompt for the rare case that needs the build tool and a proposer whose answers a deterministic checker can accept or reject. The open risks are concentrated in two places the notes could not close: the JVM without a lockfile, where the exact graph requires running Gradle or Maven, and the several CodeQL representation details that rest on snippet-level evidence and need confirming before the spec leans on them.
