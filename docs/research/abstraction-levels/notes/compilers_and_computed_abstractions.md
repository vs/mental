# Compilers and computed abstractions: how levels are defined, linked, checked and maintained

Scope: verified compilers (CompCert, CakeML), translation validation (Pnueli et al., Necula, Alive2), MLIR's multi-level IR, abstract interpretation (Cousot, Astrée, IKOS, MOPSA), predicate abstraction and its refinement loops (CEGAR, SLAM, BLAST, interpolation, CPAchecker, IC3/PDR), computed candidate invariants (Daikon, Houdini), and 2023–2026 work where an LLM proposes invariants, predicates, abstractions or translations and a checker validates them. For each system the notes answer: how levels are defined and by whom, what links adjacent levels, what is verified (once by proof, or per run by validation), how predicates and invariants are computed and maintained across program change, and what Mental can borrow given that it has an interpreter and an LLM but no theorem prover.

## At a glance

| System | What it is | How it handles levels | Take for Mental |
|---|---|---|---|
| CompCert | Verified C compiler (Coq/Rocq) | 8 intermediate languages, about 20 passes; one simulation proof per pass; register allocation validated per run by a proved checker | The pattern `if Validate(S,C) then OK else Error`; a validator must say "no" when unsure |
| CakeML | Verified ML compiler (HOL4) | 12 intermediate languages (2019 paper); a new language whenever a feature is compiled away | Add a level only when a concept disappears or appears; LLM output as an oracle with a deterministic fallback |
| Translation validation (Pnueli, Necula) | Check each run of an unverified translator | Compares code before and after each pass; simulation relation inferred by heuristics | A validator costs about one pass to build; expect false alarms (up to 10% of functions for some passes) |
| Alive2 | Bounded translation validator for LLVM IR | Checks refinement of function pairs with an SMT solver; loops unrolled to a bound | Closest model for Mental's checker: bounded, zero-false-alarm goal, explicit outcome classes |
| MLIR | Multi-level compiler IR (LLVM project) | Dialects coexist in one program; lowering by rewrite patterns toward a declared legal set; verifier checks structure only | Declare each level's legal vocabulary; allow mixed levels; structural validity is not semantic agreement |
| Abstract interpretation (Astrée, IKOS, MOPSA) | Sound static analysis by fixed points over abstract domains | Levels are a lattice of domains; the user or tool designer picks; invariants computed, widening forces termination | Default to the cheapest precision, refine where alarms appear; packs are domain-specific domains |
| Predicate abstraction / CEGAR (SLAM, BLAST, CPAchecker) | Software model checkers | Predicate set ("precision") grown from spurious counterexamples, kept per location or per function | Refine predicates from failed replays; store precisions and reuse them across commits (4× measured) |
| IC3 / PDR | SAT-based model checking | Learns clauses that are inductive relative to step-indexed frames | Invariants can be built one small lemma at a time, each from one counterexample |
| Daikon | Dynamic invariant miner | Template invariants per program point, kept if never falsified and confident above 0.99 | Mine candidate predicates and invariants from interpreter runs; label them "likely" |
| Houdini | Candidate-invariant filter | Over-propose, drop every refuted candidate, keep the greatest surviving subset | The cheapest way to use LLM proposals: many candidates, checker prunes |
| LLM + checker (Lemur, Loopy, LORIS, InvBench, …) | LLM proposes invariants; verifier decides | Proposals are assumptions until proved; filter, repair, backtrack | Generation works (78–93% on small programs); repair is weak (16%); disjunctions fail most |
| LLM-proposed abstractions (NeuroAbs, PolyVer, Agentic Model Checking) | LLM proposes an abstraction or contract; SMT/BMC checks; CEGAR refines | Abstraction per signal or per function, refined by counterexample | Prior art for "LLM proposes the level, checker validates"; narrows the draft's novelty claim |
| Validation of LLM translations (LLM-Vectorizer, LLMLift, Trivet) | Translation validation applied to LLM output | Alive2, proofs or Lean check each output | Only 38.2% of LLM vectorizations validated; plan for a large "not validated" bucket |

## 1. CompCert

### Takeaway
CompCert defines its levels as a short chain of intermediate languages, each with its own formal semantics, and proves once, per pass, a simulation diagram between the language before and the language after. The proofs compose into one end-to-end theorem. Where a pass is hard to prove (graph-colouring register allocation), CompCert runs unverified code and checks its result on every compilation with a small checker that is itself proved sound. The draft report's "about twenty intermediate languages" is wrong: there are 8 intermediate languages and about 20 passes.

### Cited Findings
- [V] The current development lists the source language CompCert C, eight intermediate languages (Clight, Csharpminor, Cminor, CminorSel, RTL, LTL, Linear, Mach) and the target Asm. It lists 20 passes; 11 of them stay inside one language (for example eight RTL → RTL optimizations). — [CompCert commented development](https://compcert.org/doc/index.html)
- [V] The user manual states the count as "8 intermediate languages and 15 compilation passes"; the 2009 paper says "14 passes that go through 8 intermediate languages". The pass count has grown; the language count has not. — [CompCert manual §1](https://compcert.org/man/manual001.html); [Leroy, CACM 2009](https://xavierleroy.org/publi/compcert-CACM.pdf)
- [V] The link between adjacent levels is a simulation diagram: "each transition in the original program must correspond to a sequence of transitions in the transformed program that have the same observable effects" and preserve a relation ∼ between the states of the two programs. For register allocation the diagram is "lock-step" (one transition to exactly one). Observable effects are traces of input-output operations. — [Leroy, CACM 2009, §4.3](https://xavierleroy.org/publi/compcert-CACM.pdf)
- [V] Levels are chosen by the compiler authors, and every one must be given a formal semantics: "all intermediate languages must be given appropriate formal semantics". Each intermediate language costs 300–600 lines of Coq; each pass costs 1,500–3,000 lines for its specification and proof. — [Leroy, CACM 2009, §2.3, §3.3](https://xavierleroy.org/publi/compcert-CACM.pdf)
- [V] Cost: 42,000 lines of Coq and about 3 person-years in 2009; 76% of the lines are proof, 14% are the compilation algorithms, 10% are language semantics. Generated code was about 7% slower than `gcc -O1` and 12% slower than `gcc -O2`. — [Leroy, CACM 2009, §3.3](https://xavierleroy.org/publi/compcert-CACM.pdf)
- [V] Per pass there is a choice "between proving the code that implements this pass or performing the transformation via untrusted code, then verifying its results using a verified validator". A validator is a Boolean function `Validate(S, C)`; it is *verified* if `Validate(S,C) = true ⟹ S ≈ C` is proved. Then `Comp'(S) = match Comp(S) with Error → Error | OK(C) → if Validate(S,C) then OK(C) else Error` is as trustworthy as a verified compiler. — [Leroy, CACM 2009, §2.2–2.3](https://xavierleroy.org/publi/compcert-CACM.pdf)
- [V] Validators are "necessarily incomplete and should reply false if they cannot establish S ≈ C". An *unverified* validator gives weaker guarantees because "the validator could itself be incorrect". — [Leroy, CACM 2009, §2.2](https://xavierleroy.org/publi/compcert-CACM.pdf)
- [V] Register allocation is the validated pass. The colouring heuristic is "unverified Caml code"; three conditions on the colouring are checked by Boolean functions proved in Coq, and "compilation is aborted if the checks fail". The current pass table labels exactly one pass this way: "Register allocation (validation a posteriori)". — [Leroy, CACM 2009, §4.2](https://xavierleroy.org/publi/compcert-CACM.pdf); [CompCert commented development](https://compcert.org/doc/index.html)
- [V] The later register-allocation validator works by "backward dataflow inference of equations between variables, registers and stack locations", and its soundness is proved in Coq. Verified validators were also built for list scheduling and trace scheduling; the 2009 paper mentions lazy code motion and scheduling as validator-style passes developed separately. — [Rideau & Leroy, CC 2010](https://xavierleroy.org/publi/validation-regalloc.pdf); [Tristan & Leroy, POPL 2008](https://xavierleroy.org/publi/validation-scheduling.pdf); [Leroy, CACM 2009, §3.2](https://xavierleroy.org/publi/compcert-CACM.pdf)
- [V] Not everything is proved. Preprocessing lacks a specification; for assembling and linking "we have no formal guarantees yet"; AbsInt's Valex tool gives "additional assurance via a posteriori validation of the executable". The theorem itself is one-directional: the behavior of the compiled code "improves on one of the allowed observable behaviors" of the source. — [CompCert manual §1](https://compcert.org/man/manual001.html)

### Inferences
- Mental's level checker is a validator in Leroy's exact sense, and an *unverified* one. The honest claim is "this pair of levels was checked on these scenarios within these bounds", not "the upper level is correct".
- The `Comp'` wrapper is the right contract for every LLM stage: output that fails validation is an error or a quarantined judgment record, never a silently accepted level.
- "Reply false if unsure" translates to: a pair that the interpreter could not fully explore within its bounds is reported as *not validated*, with the reason, and is distinct from *refuted*.
- CompCert validates the pass whose algorithm is a heuristic search (colouring) and proves the passes that are simple rewrites. Mental's analogue: deterministic extractors need no per-run validation beyond tests; LLM stages always do.
- CompCert's simulation is stated over observable traces. Mental needs the same decision per level pair: which events are observable at the upper level (replies, sends, store writes visible above), so that everything else may stutter.

### Gaps
- Proof effort for the current (2026) development was not found; the 42,000-line figure is from 2009.
- The lock-step, "plus" and "star with measure" diagram variants are described in Leroy's JAR 2009 backend paper, which was not opened. (training knowledge; not re-fetched)

## 2. CakeML

### Takeaway
CakeML follows CompCert's architecture in HOL4 but states an explicit rule for when to add a level: introduce a new intermediate language whenever a significant higher-level feature has been compiled away or a new lower-level one is introduced. Its only use of translation validation is for speed during bootstrapping, with a proved algorithm as the fallback.

### Cited Findings
- [V] The compiler is "a sequence of intermediate languages through which high-level features are compiled away incrementally", which "enables verification of each compilation pass at an appropriate level of semantic detail". The 2019 paper describes 12 intermediate languages and five targets; the project site today says "8 intermediate languages" and 6 architectures. — [Tan et al., JFP 2019](https://cakeml.org/jfp19.pdf); [cakeml.org](https://cakeml.org/)
- [V] Design decision D0: fewer languages allow reuse of lemmas, but languages that support both higher- and lower-level features "can complicate the invariants needed to verify transformations, especially when no program will contain both at the same time". So "our CakeML compiler introduces a new intermediate language whenever a significant higher-level language feature has been compiled away, or when a new lower-level one is introduced"; "many transitions work within a single IL". — [Tan et al., JFP 2019, §2.1](https://cakeml.org/jfp19.pdf)
- [V] Translation validation is used only for efficiency: the register allocator "takes an optional list of oracle colouring functions"; it "validates that they correctly colour the program"; "otherwise, it calls the graph colouring algorithm that we have proved always produces a correct colouring". The bootstrapped compiler runs the verified algorithm directly. — [Tan et al., JFP 2019, §11.3.1](https://cakeml.org/jfp19.pdf)
- [V] Cost: "approximately 100000 lines of HOL4 proof scripts". The compiler "has been bootstrapped inside HOL". — [Tan et al., JFP 2019, §14](https://cakeml.org/jfp19.pdf); [cakeml.org](https://cakeml.org/)
- [V] A separate front end, the "translator", is proof-producing: it "generates CakeML AST from ML-like functions in HOL and proves that the generated AST has the same behaviour as the HOL function". That is a certificate per run, not a proof of the tool. — [cakeml.org](https://cakeml.org/)

### Inferences
- D0 is a usable test for Mental's inserted levels and domain ladders: a level earns its place only if some vocabulary disappears going up (or appears going down). A level whose vocabulary equals its neighbor's is a view, not a level. This is the same point as the draft's "many thin levels" recommendation, with a criterion attached.
- The oracle-with-fallback design fits LLM summaries. The LLM's summary cases are an oracle; if they validate against the full graph they are used; if not, Mental falls back to a mechanically derived summary (the enumerated paths of the full graph, unnamed and ugly but correct).
- The two published counts (12 in 2019, 8 today) show that the number of levels in a mature system is not stable. The ladder should be data, not code.

### Gaps
- The site's "8 intermediate languages" was not reconciled with the paper's 12; the current language list was not opened.
- How CakeML's proofs are maintained when a pass changes was not found.

## 3. Translation validation: Pnueli et al., Necula, Alive2

### Takeaway
Translation validation checks each run of a translator instead of proving the translator. Twenty-five years of practice give three numbers worth keeping: a validator for GCC took about the effort of one compiler pass to build, slowed compilation fourfold and raised false alarms on up to 10% of functions for some passes; Alive2, designed for zero false alarms and bounded resources, found 47 new LLVM bugs by re-checking the existing unit tests. Both check *refinement* (the target shows a subset of the source's behaviors), not equality.

### Cited Findings
- [S] Pnueli, Siegel and Singerman, "Translation Validation", TACAS 1998 — bibliographic data confirmed; the paper was not opened (paywalled). — [doi:10.1007/BFb0054170](https://doi.org/10.1007/BFb0054170)
- [B] The 1998 paper validated a code generator from the synchronous language Signal to C, treating both programs as transition systems and having the translator emit a proof script that a separate proof checker checks; correctness is stated as refinement. (training knowledge; not re-fetched)
- [V] Necula's validator for GCC "compares the intermediate form of the program before and after each compiler pass and verifies the preservation of semantics". It "does not rely on help from the optimizer" but uses "a few heuristics to detect the transformations that take place". The equivalence criterion is a simulation relation between the two programs, and the validator acts as "an inferencer for simulation relations", using symbolic evaluation. — [Necula, PLDI 2000](https://people.eecs.berkeley.edu/~necula/Papers/tv_pldi00.pdf)
- [V] Necula's cost and precision: the infrastructure "can be implemented with about the effort typically required to implement one compiler pass"; it "slows down compilation by a factor of four"; "for most optimizations the ratio of false alarms is very low but for some others there is a false alarm in about 10% of the compiled functions". It handled GCC compiling itself and the Linux kernel, and isolated a known bug in GCC 2.7.2.2. — [Necula, PLDI 2000](https://people.eecs.berkeley.edu/~necula/Papers/tv_pldi00.pdf)
- [V] Alive2 is "a bounded translation validation tool" for LLVM IR that "limits resource consumption by, for example, unrolling loops up to some bound, which means there are circumstances in which it misses bugs". It "is designed to avoid false alarms, is fully automatic through the use of an SMT solver, and requires no changes to LLVM". — [Lopes et al., PLDI 2021](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf)
- [V] What Alive2 checks: "pairs of functions in LLVM IR for refinement. A refinement relation is satisfied when, for every possible input state, a target function displays a subset of the behaviors of a source function. Refinement allows a transformation to remove non-determinism, but not to add it." It "works with any intra-procedural optimization". — [Lopes et al., PLDI 2021, §1](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf)
- [V] Alive2 is used both per pass (plugins "to check refinement after every optimization pass") and on arbitrary pairs of IR files. — [Lopes et al., PLDI 2021, §1](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf)
- [V] Results: 121 refinement violations in LLVM's unit tests, of which 15 were bugs in Alive2 or tests designed to fail; 47 bugs reported, 28 fixed at publication; eight patches to the LLVM Language Reference. The whole unit-test suite runs under Alive2 in "about 2.5 hours on an 8-core Intel workstation". More unrolling means fewer passed tests "due to timeout or out-of-memory". — [Lopes et al., PLDI 2021, §8.2](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf)
- [V] Alive2 reports outcomes per pair in separate classes: validated, violation of refinement, timeout, out of memory, and "at least one feature unsupported by Alive2". — [Lopes et al., PLDI 2021, §8.3](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf)
- [V] Why re-checking existing tests found bugs: Alive2 "is a far more discerning test oracle than are the syntactic oracles" built into the unit tests. — [Lopes et al., PLDI 2021, §8.2](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf)
- [S] Alive (PLDI 2015), the predecessor, verified peephole optimizations written in a small DSL rather than validating compiler runs. — [Lopes et al., PLDI 2015](https://users.cs.utah.edu/~regehr/papers/pldi15.pdf)

### Inferences
- Mental's refinement check by projection is bounded translation validation in Alive2's sense. Adopt its vocabulary: say "bounded", publish the bound (loop iterations, schedule depth, input classes covered), and keep five outcome classes per level pair: *validated within bounds*, *refuted with a counterexample run*, *timeout*, *unsupported construct*, *checker error*.
- The direction of refinement matters. Going down (compiling), the lower level may remove nondeterminism. Going up (Mental's direction), the upper level may *add* behaviors (an over-approximation) but may not *lose* any lower behavior. A summary that drops a real case is the unsound direction; a summary with an unreachable case is merely imprecise. The checker should report the two differently.
- Necula inferred the simulation relation with heuristics and paid with false alarms; Alive2 needs no relation because source and target share one language. Mental's levels differ in vocabulary, so it needs the relation (the abstraction function) to be given. Asking the LLM to emit it alongside the level is the equivalent of Pnueli's translator emitting a proof script, and Necula's "optimizer communicates to the validator what transformations were performed".
- Alive2's biggest side effect was fixing the *semantics document*. Expect the same: refinement failures will often expose an ambiguity in Mental's model language rather than a bad LLM answer.
- "A far more discerning oracle" suggests a cheap first experiment: run the pair check over scenarios Mental already has, before generating new ones.

### Gaps
- The Pnueli paper was not read; its mechanism above is from memory.
- No source was found on translation validation where source and target are in *different* vocabularies and the relation is supplied by an untrusted party, which is Mental's case. The nearest are verified lifting (section 9) and Necula's "framework that the optimizer can use to communicate".

## 4. MLIR: many levels in one infrastructure

### Takeaway
MLIR is the closest structural precedent for a ladder that is data rather than code. Levels are *dialects*: namespaced sets of operations, types and attributes that anyone can define, and operations from different dialects can sit side by side in one function. Lowering is a set of rewrite patterns driven toward a declared *conversion target* (which operations are legal), applied partially or fully. What MLIR verifies after each step is structural validity of the IR, not that the lowering preserved meaning; semantic checks arrived later as separate research tools.

### Cited Findings
- [V] Design principle "progressive lowering": "from the higher-level representation down to the lowest-level, with the lowering being performed in small steps along multiple abstraction levels". Earlier compilers had fixed levels (Open64 WHIRL has five; Clang lowers AST → LLVM IR → SelectionDAG → MachineInstr → MCInst) "in a rigid way". — [Lattner et al., "MLIR", arXiv 2002.11054, §2](https://arxiv.org/pdf/2002.11054)
- [V] Design principle "maintain higher-level semantics": "Attempts to raise semantics once lowered are fragile"; "the loss of structure is then conscious and happens only where the structure is no longer needed". As a corollary, "mixing different levels of abstractions and different concepts in the same IR is a key property of the system to allow a part of the representation to remain in higher-level abstraction while another part is lowered". — [Lattner et al., arXiv 2002.11054, §2](https://arxiv.org/pdf/2002.11054)
- [V] "Each Op, type and attribute belongs to exactly one dialect"; "Ops from different dialects can coexist at any level of the IR at any time". The language reference: "MLIR allows for multiple dialects, even those outside of the main tree, to co-exist together within one module"; each dialect has "a unique namespace". — [Lattner et al., arXiv 2002.11054, §4](https://arxiv.org/pdf/2002.11054); [MLIR Language Reference](https://mlir.llvm.org/docs/LangRef/)
- [V] Who defines levels: anyone. MLIR is "an open system; it is designed to support modular and pluggable dialects", and "dialects are expected to verify the allowable operation types per operation". — [MLIR Rationale](https://mlir.llvm.org/docs/Rationale/Rationale/)
- [V] What links levels: dialect conversion. "The conversion target is a formal definition of what is considered to be legal during the conversion process." Each operation is marked Legal ("every instance … is legal"), Dynamic ("only some instances", decided by a callback) or Illegal ("no instance … is legal"). — [MLIR Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)
- [V] Patterns "do not need to generate operations that are directly legal on the target"; "the framework will automatically build a graph of conversions", so `bar.add → baz.add` and `baz.add → foo.add` legalize `bar.add` to `foo.add` "even though a direct conversion does not exist". — [MLIR Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)
- [V] Conversion modes: *partial* ("legalize as many operations to the target as possible"; unknown operations may remain), *full* (succeeds only if "all operations are properly legalized"), and *analysis* (reports what would convert without rewriting). When value types change between levels, source and target *materializations* insert conversions at the boundary; "if a materialization is required, but cannot be performed, the entire conversion process fails". — [MLIR Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)
- [V] What is verified per level: "Verifiers are used to enforce structural correctness of the IR and invariants of Ops, allowing passes to assume a verified IR". Checks start with whole-IR structure (types match, single definition, dominance, terminators), then per-operation and per-attribute verifiers. "Verification failures are considered invariant violations and abort compilation." Traits "often describe verification constraints on valid IR". — [Lattner et al., arXiv 2002.11054, §4.6](https://arxiv.org/pdf/2002.11054); [MLIR Language Reference](https://mlir.llvm.org/docs/LangRef/)
- [V] The paper asks for validation to be "as declarative as practical, providing a single source of truth". — [Lattner et al., arXiv 2002.11054, §2](https://arxiv.org/pdf/2002.11054)
- [V] What is *not* verified: "A major limitation of MLIR is that it is syntax-focused: it has no support for directly encoding the semantics" of operations. The 2025 fix defines each dialect's semantics *as a lowering* to a small set of semantics dialects ending in SMT; with it the authors gave semantics to five dialects, found five miscompilation bugs in upstream MLIR and verified a canonicalization pass. — [Fehr et al., "First-Class Verification Dialects for MLIR", PLDI 2025](https://pldi25.sigplan.org/details/pldi-2025-papers/60/First-Class-Verification-Dialects-for-MLIR)
- [S] Earlier SMT-based translation validators for MLIR exist (mlir-tv, 2022) and reported ambiguities in MLIR's semantics. — [Bang et al., CAV 2022, doi:10.1007/978-3-031-13188-2_19](https://doi.org/10.1007/978-3-031-13188-2_19)

### Inferences
- A level in Mental can be declared the MLIR way: a namespace plus a *legal set* (which entity kinds, step kinds and predicate families may appear). "The abstraction barrier" from the checkpoint is then MLIR's full-conversion check: a view at level L is valid if nothing illegal at L remains in it. This is cheap, deterministic and can be built before the interpreter.
- Partial conversion is exactly zoom: part of the picture stays at the service level while one behavior is opened to statements. MLIR shows that mixed-level programs are workable if the boundary is explicit. Its materializations are Mental's adapters at a zoom boundary: where a business-level message meets a statement-level handler, something must convert the vocabulary, and a missing conversion is a failure, not a silent pass.
- The transitive legalization graph says the LLM need not supply a direct map from statements to business. A chain of adjacent maps composes. This supports the draft's "check per adjacent pair".
- The Dynamic legality class (legal only for some instances, by a predicate) matches packs: a Postgres row lock is legal at the mechanism level only when the pack's condition holds.
- MLIR's history is a warning. It shipped structural verification and called it validation; semantic bugs in lowerings were found only once semantics were written down (five upstream bugs). Mental's anchor, coverage and partition checks are the structural layer. They do not show that a summary means the same as the code. Only running both levels does.
- "Attempts to raise semantics once lowered are fragile." Mental's whole direction is raising. MLIR's answer was to avoid raising by keeping structure. Mental cannot, so it must check each raise. The 2025 trick is still usable in reverse: define an upper-level step's meaning *as* its lowering (the anchored lower steps), which is what the refinement map already is.

### Gaps
- No MLIR source states how many dialects a typical pipeline crosses or what legalization failures cost in practice.
- IRDL (declarative dialect definitions) and the Transform dialect were not opened.

## 5. Abstract interpretation: Cousot, Astrée, IKOS, MOPSA, Goblint

### Takeaway
In abstract interpretation a level is an abstract domain: a lattice of properties with operations that over-approximate the program's steps. Domains themselves are ordered by precision, are chosen by the tool's designer or by a command-line flag, and are combined in products. Invariants are never authored; they are the fixed point of the abstract semantics. Industrial precision came from adding domains specialized to one family of programs, and at least one analyzer reuses fixed-point results across program edits.

### Cited Findings
- [V] The 1977 paper: "Abstract program properties are modeled by a complete semilattice"; "levels of abstraction are formalized by showing that consistent abstract interpretations form a lattice"; finite fixed-point approximation methods are introduced for when the iteration sequences are infinite. — [Cousot & Cousot, POPL 1977 (author page)](https://www.di.ens.fr/~cousot/COUSOTpapers/POPL77.shtml)
- [V] The 1979 paper relates the concrete and abstract lattices by Galois connections, and studies the "sum", "product" and "power" of analysis frameworks; combined analyses give more precise results than running them separately and conjoining the answers, but this "can only be achieved by a new design of the approximate predicate transformer". — [Cousot & Cousot, POPL 1979 (author page)](https://www.di.ens.fr/~cousot/COUSOTpapers/POPL79.shtml)
- [B] A Galois connection is a pair of monotone maps, abstraction α and concretization γ, such that α(c) ⊑ a exactly when c ⊆ γ(a). Widening is an operator that jumps ahead in the lattice so that iteration at loops terminates, at a cost in precision; narrowing recovers some of it. The term "reduced product" (domains exchange information after each step) comes from the 1979 paper. (training knowledge; not re-fetched)
- [V] Astrée proves absence of run-time errors in C and is sound ("always"), at the price of possible false alarms. In November 2003 it proved the absence of any run-time error in the primary flight control software of the Airbus A340: 132,000 lines of C, analyzed in 1h20 on a 2.8 GHz PC with 300 MB, with zero false alarms; from 2004 it was extended to the A380. — [Astrée project page](https://www.astree.ens.fr/)
- [V] How Astrée reached zero false alarms: it is specialized to a program family (synchronous, time-triggered embedded C, no dynamic allocation or recursion), and "domain-aware": besides intervals and octagons it has domains written for control software (digital filters, arithmetic-geometric progressions), trace partitioning for disjunctions, all combined through a weak form of reduced product. It is parametric (users tune cost against precision) and extensible (new domains are added when false alarms appear). — [Astrée project page](https://www.astree.ens.fr/)
- [V] IKOS (NASA) is a C/C++ analyzer offering generic "fixpoint iterators, numerical abstract domains". The user picks the domain with `-d`: interval, congruence, DBM, gauge, octagon, polyhedra and variants. "By default, IKOS uses the fastest and least precise numerical domain, the interval domain." Widening is tunable: delay (default 1), period, strategy, widening hints (on by default), and a narrowing strategy. Checks are selected with `-a` (buffer overflow, division by zero, null dereference, user assertions, …). — [IKOS README](https://github.com/NASA-SW-VnV/ikos); [IKOS analyzer README](https://github.com/NASA-SW-VnV/ikos/blob/master/analyzer/README.md)
- [V] MOPSA builds each analysis from "a constellation of small abstract domains" with low coupling, combined through reduced products and a shared expression-rewriting mechanism; it supports C, Python 3 and mixed C/Python, took part in SV-COMP 2024, and states it "may not be ready yet for production". — [MOPSA](https://mopsa.lip6.fr/)
- [V] Maintenance across change: Goblint's interactive abstract interpretation makes a whole-program analysis incremental using a fixed-point engine that tracks dependencies between unknowns and lazily invalidates affected results after an edit; re-analysis after small changes "only takes a fraction of from-scratch analysis time" with most precision retained. No figure is given in the abstract. — [Erhard et al., "Interactive Abstract Interpretation", arXiv 2209.10445](https://arxiv.org/abs/2209.10445)
- [S] The earlier paper (Seidl, Erhard, Vogler, 2020) shows that the top-down local solver can reuse earlier results by recursively destabilizing the unknowns that depend on a change. — [doi:10.1007/978-3-030-41103-9_5](https://doi.org/10.1007/978-3-030-41103-9_5)

### Inferences
- A "precision level" in this family is chosen, not discovered: by a flag (IKOS), by tool designers after looking at alarms (Astrée), or by composition (MOPSA). The draft's sentence "the level is chosen by choosing the domain, once per analysis" is right for IKOS but understates Astrée, where the level was refined over months by people adding domains, and section 6, where it is adjusted during the run.
- Astrée's lesson maps directly to packs. Generic domains gave alarms; domains that encode what a digital filter *is* removed them. A pack that knows what a connection pool or a `SELECT … FOR UPDATE` is plays the same role. Zero false alarms was achieved for one program family, not in general.
- Mental's named predicates are a small abstract domain per behavior. The reduced-product idea says: keep several families (message-field predicates, stored-state predicates, config predicates) and let a fact learned in one prune another, rather than building one big vocabulary.
- IKOS's default (cheapest domain first) is a good default for zoom: build the summary level everywhere, compile the full graph only where a check fails or the user looks.
- Widening is what an interpreter without a prover lacks. Mental's bounded exploration stops at a bound instead of generalizing. Any invariant it reports is "held up to bound k", closer to Alive2 than to Astrée. That limit should be visible in the result.
- The Goblint design (track which results depend on which inputs, invalidate lazily) is the model for caching level-pair checks across commits.

### Gaps
- No primary source was opened for widening and reduced product definitions.
- No measured figure for Goblint's incremental speedup was extracted.
- Infer's compositional, diff-time analysis was not covered.

## 6. Predicate abstraction, CEGAR, SLAM, BLAST, interpolation, CPAchecker, IC3/PDR

### Takeaway
This family computes its own level. The abstraction is a set of predicates; the model checker explores the abstract program; a counterexample that cannot be replayed on the real program is *spurious*, and the reason it fails yields new predicates. CPAchecker names the predicate set a *precision*, stores it per program location or per function, and has measured that reusing stored precisions on later revisions cuts analysis time by a factor of more than four. This corrects the draft's statement that maintenance across change means re-running from scratch everywhere.

### Cited Findings
- [S] Graf and Saïdi (CAV 1997) build an abstract state graph automatically from a program and "a partition of the state space induced by a finite set of predicates", using the PVS prover to decide, for each predicate, whether it or its negation holds after a step. — [Graf & Saïdi, SRI page](https://csl.sri.com/papers/grafsaidi97/)
- [S] Clarke, Grumberg, Jha, Lu and Veith (CAV 2000; JACM 50(5), 2003): an automatic iterative abstraction-refinement method; an abstract counterexample that the concrete model cannot follow is "spurious", and the abstraction is refined by splitting the abstract state where the replay fails; finding the coarsest refinement is NP-hard. — [Clarke et al., Stanford-hosted copy](https://cs357.stanford.edu/cegar.pdf)
- [V] SLAM checks "that software satisfies critical behavioral properties of the interfaces it uses"; Static Driver Verifier, shipped in the Windows Driver Kit, "uses the SLAM verification engine"; Boolean programs are "the internal language used for the model checking step". The SLAM2 paper is titled "Static Driver Verification with Under 4% False Alarms" (FMCAD 2010). — [SLAM project page](https://www.microsoft.com/en-us/research/project/slam/)
- [S] The CACM retrospective: SLAM's abstractions keep only predicates relevant to the property being checked and are refined automatically from the model checker's counterexamples; goals were scalability and a very low false-error rate. — [Ball, Levin, Rajamani, CACM 2011](https://cacm.acm.org/magazines/2011/7/109893-a-decade-of-software-model-checking-with-slam/fulltext)
- [B] SLAM's loop has three tools: C2BP abstracts a C program and a predicate set into a Boolean program, Bebop model-checks it, and Newton analyses an infeasible path to find new predicates. (training knowledge; not re-fetched)
- [S] Lazy abstraction (Henzinger, Jhala, Majumdar, Sutre, POPL 2002) "continuously builds and refines a single abstract model on demand, driven by the model checker", so that precision varies across parts of the model; implemented for C in BLAST. — [ISTA record](https://research-explorer.ista.ac.at/record/4476)
- [B] "Abstractions from Proofs" (Henzinger, Jhala, Majumdar, McMillan, POPL 2004) takes new predicates from Craig interpolants of the infeasible path formula: an interpolant at a cut point is a formula over the variables live there that the prefix implies and the suffix contradicts, so each location gets only the predicates it needs. (training knowledge; not re-fetched)
- [V] CPAchecker is "a tool for configurable software verification" built on "Configurable Software Verification" (CAV 2007) and "Program Analysis with Dynamic Precision Adjustment" (ASE 2008); at SV-COMP 2026 it won five medals including silver overall. — [CPAchecker](https://cpachecker.sosy-lab.org/)
- [V] Definition: "A precision is the information that an abstraction-based analysis uses to guide the abstraction computation." For predicate abstraction "a precision is a set of predicates over program variables"; for explicit-value analysis it is a list of variables to track. "The empty precision is the coarsest." With block encoding, predicates are relevant only at loop heads. — [Beyer et al., "Precision Reuse for Efficient Regression Verification", ESEC/FSE 2013, §2–3](https://www.sosy-lab.org/research/pub/2013-FSE.Precision_Reuse_for_Efficient_Regression_Verification.pdf)
- [V] Precisions "are reasonably small and thus easy to store; they are easy to process and have a large impact on resource consumption". Study: 16,772 verification runs for 4,193 tasks from 1,119 revisions of 62 Linux drivers. Reuse speeds up predicate analysis "by a factor greater than 4" on average; when a complete precision from an earlier "safe" result is available, "refinements are eliminated completely". There is no speedup when the earlier run stopped early at a bug. — [Beyer et al., ESEC/FSE 2013, §1](https://www.sosy-lab.org/research/pub/2013-FSE.Precision_Reuse_for_Efficient_Regression_Verification.pdf)
- [V] Scoping a stored precision: *function-scoped* (the union of a function's predicates is assigned to all its locations) "is insensitive to changes of the control-flow structure within functions" but is lost on rename; *location-scoped* is exact but "location ids may change if the program code was changed". A reused precision is only a starting point; soundness does not depend on it because the analysis still runs. — [Beyer et al., ESEC/FSE 2013, §3](https://www.sosy-lab.org/research/pub/2013-FSE.Precision_Reuse_for_Efficient_Regression_Verification.pdf)
- [V] Cost profile: tasks where the property holds need "a large number of refinements (> 20) and expensive abstraction computations (> 500)", because the whole state space must be covered; violating tasks stop early. — [Beyer et al., ESEC/FSE 2013, §1](https://www.sosy-lab.org/research/pub/2013-FSE.Precision_Reuse_for_Efficient_Regression_Verification.pdf)
- [S] IC3 (Bradley, VMCAI 2011) "incrementally generates clauses that are inductive relative to (and augment) stepwise approximate reachability information", without unrolling the transition relation; a typical run issues tens of thousands of small SAT queries and produces hundreds or thousands of lemmas. — [VMCAI 2011 bibliographic page](https://bibtex.github.io/VMCAI-2011-Bradley.html)
- [V] The underlying idea in lecture form: a property P is usually not inductive, "but a stronger inductive invariant F may exist" with INIT ⇒ F, F ∧ T ⇒ F′ and F ⇒ P; IC3 finds F as a conjunction of clauses. — [IC3 lecture slides, Tel Aviv University](https://www.cs.tau.ac.il/~msagiv/courses/asv/IC3.pdf)

### Inferences
- Mental's predicates per behavior are a precision in CPAchecker's sense. Store them as a first-class, small artifact keyed by behavior (function-scoped), not by statement position, because the measured result is that function scope survives edits. On a new commit, start from the stored predicate set and re-validate, instead of asking the LLM again. This also makes LLM output more stable across runs.
- CEGAR without a prover: run a scenario at the summary level; replay it on the full graph. If the replay fails at some step, the summary allowed a path the code does not have. The failing step names the test in the code that separated the two; that test, or a predicate the LLM names for it, is the refinement. The interpreter plays Newton; no interpolation engine is needed because the full graph's guards are already anchored tests.
- The opposite failure (the full level has a path with no summary case) has no CEGAR analogue, because CEGAR's abstraction is sound by construction. In Mental the abstraction is proposed, not constructed, so both directions must be checked. This is the main difference from this whole family and it should be stated in the report.
- Lazy abstraction's point is that refinement is local. A failed summary for one port should re-open that port only.
- "Holds" is expensive, "violated" is cheap (>20 refinements against early exit). Mental's budgets should expect the same asymmetry: confirming a level pair costs far more than refuting it.
- IC3 suggests how to grow level invariants without a prover: each bounded-exploration counterexample to an invariant yields one small lemma (one more predicate conjunct) rather than a rewritten invariant.

### Gaps
- Lazy abstraction, interpolation, CEGAR and Graf–Saïdi were not read in full; SLAM's tool chain and numbers beyond the SLAM2 title are from memory.
- "Dynamic precision adjustment" (changing the precision during a run) is confirmed only by title.
- No source on reusing precisions when the *abstraction itself* came from an LLM.

## 7. Computed candidate invariants: Daikon and Houdini

### Takeaway
Two older techniques compute invariants without a prover-driven search, and both fit an interpreter. Daikon proposes template invariants and keeps those never falsified by observed runs. Houdini takes any set of candidates and repeatedly drops those the checker refutes, returning the largest set that survives together. Recent LLM work reuses Houdini directly.

### Cited Findings
- [V] Daikon performs "dynamic detection of likely invariants": an instrumenter records variable values at program points (`:::ENTER`, `:::EXIT`, `:::OBJECT`, `:::CLASS`), and Daikon reports properties from a built-in catalog of templates (bounds, equalities, one-of sets, sequence properties) that held in every observed execution. — [Daikon user manual](https://plse.cs.washington.edu/daikon/download/doc/daikon.html)
- [V] Filtering: each invariant type has a confidence computation; an invariant is reported only above a limit that "defaults to .99", to exclude patterns that held by chance. Daikon "never outputs invariants that were ever false". The results are "likely" invariants: unobserved executions may violate them. — [Daikon user manual](https://plse.cs.washington.edu/daikon/download/doc/daikon.html)
- [S] Houdini (Flanagan & Leino, FME 2001) "generates a large number of candidate annotations and uses ESC/Java to verify or refute each of them", repeating until nothing more is removed; it "computes the greatest subset" of the candidate set that is valid for the program. — [Flanagan & Leino, doi:10.1007/3-540-45251-6_29](https://link.springer.com/doi/10.1007/3-540-45251-6_29); [Ernst et al. annotation study, FSE 2002](https://homes.cs.washington.edu/~mernst/pubs/annotation-study-fse2002.pdf)
- [V] Houdini applied to LLM output: it makes at most one checker call per candidate, and raised the number of solved loop-invariant benchmarks from 293 to 383 of 469 (a 30.7% increase) in the Loopy study. — [Kamath et al., arXiv 2311.07948](https://arxiv.org/html/2311.07948)
- [V] An LLM fine-tuned to predict invariants statically produced results of quality "comparable to those obtained by a dynamic analysis tool with access to five program traces". — [Pei et al., "Can Large Language Models Reason about Program Invariants?", ICML 2023](https://proceedings.mlr.press/v202/pei23a.html)

### Inferences
- The interpreter's runs are Daikon traces. At each port and each level, record projected state and mine template invariants ("status is one of {pending, running, done}", "at most one courier per order"). They are candidates only.
- Houdini is the right aggregation for LLM proposals: ask for many candidate invariants or predicates, run bounded exploration, drop each one that some run falsifies, keep the rest. It needs no repair dialogue and its cost is linear in the number of candidates.
- Daikon's 0.99 confidence rule guards against a real risk for Mental: an invariant that "held" only because few scenarios reached that port. Report the number of observations behind each surviving invariant.
- Houdini's result is conjunctive. It cannot discover a case split. That limit shows up again in section 8 as the main failure class.

### Gaps
- The Houdini paper was not opened.
- Daikon's performance on systems of Mental's target size was not looked up.

## 8. LLMs proposing invariants, predicates and abstractions for a checker (2023–2026)

### Takeaway
The settled architecture is "the LLM proposes, a sound checker decides", with proposals treated as assumptions until proved. On small single-loop programs, success rates are now 78–93%, and LLM pipelines solve some problems symbolic tools cannot, while still solving fewer overall in one head-to-head study. Repairing a wrong proposal works far worse than generating a fresh one, and invariants that need a disjunction are the largest failure class. Since 2025 the same pattern has been applied to abstractions and contracts inside CEGAR loops, which is close to what Mental plans.

### Cited Findings
- [V] LEMUR defines a proof calculus over an LLM (propose and repair oracles) and a verifier that answers True, False or Unknown. "Properties generated by an LLM are treated as assumptions until we can prove that they are invariants." Soundness is proved; termination is forced by capping proposals per goal at k. Rules include backtracking from a bad assumption and repair when a proposal is falsified or does not imply the goal. — [Wu, Barrett, Narodytska, "Lemur", arXiv 2310.04870](https://arxiv.org/html/2310.04870)
- [V] LEMUR numbers: on 133 Code2Inv benchmarks, ESBMC alone solves 68, Code2Inv 92, LEMUR 103 (GPT-3.5) and 107 (GPT-4), with 4.7 proposals on average for GPT-4. On 47 SV-COMP tasks that ESBMC and UAutomizer could not solve in 10 minutes, each tool alone solves 1; LEMUR solves 14 (GPT-3.5) and 25 (GPT-4). Without the repair rules GPT-4 solved 19–20. Results vary between runs. Stated limits: small programs, multiple loops, nested formulas. — [Lemur, arXiv 2310.04870](https://arxiv.org/html/2310.04870)
- [V] Loopy (Microsoft): on 469 single-loop C benchmarks with GPT-4 and at most 15 completions each, raw LLM output solves 293; with Houdini filtering 383; with repair 398 (84.9%). The symbolic verifier Ultimate solves 430, but Loopy solves 31 that Ultimate does not. Of the 71 failures, 44 needed disjunctions, 10 were checker failures, 9 needed more precise constraints. — [Kamath et al., "Finding Inductive Loop Invariants using LLM-based Reasoning", arXiv 2311.07948](https://arxiv.org/html/2311.07948)
- [V] Ranking: LLMs "often need several attempts" to produce a correct invariant, and each failed attempt costs a verifier call; a learned re-ranker moves correct candidates forward and cuts calls. — [Chakraborty et al., arXiv 2310.09342](https://arxiv.org/abs/2310.09342)
- [V] AutoSpec: static analysis decomposes the program, the LLM proposes specifications per piece, and candidates are validated each round "to prevent error accumulation"; 79% of programs verified, 1.592× the prior work; applied to an X509 parser. — [Wen et al., CAV 2024, arXiv 2404.00762](https://arxiv.org/abs/2404.00762)
- [V] "How far are we?" study (Nov 2025): across open and closed models, loop-invariant *generation* reaches at most 78% success; *repair* of incorrect invariants reaches at most 16%. Domain knowledge and examples in the prompt help substantially. — [Akhond et al., arXiv 2511.06552](https://arxiv.org/abs/2511.06552)
- [V] InvBench (Sep 2025; four versions through Aug 2026): 866 evaluation instances derived from SV-COMP and 3,589 training instances; nine LLMs. It checks each proposed invariant with a sound procedure and measures whether it actually helps verification; fine-tuning and best-of-N sampling both help. — [Wei et al., "InvBench", arXiv 2509.21629](https://arxiv.org/abs/2509.21629)
- [V] LORIS (May 2026): when a proposed invariant fails a verification condition, the LLM writes a step-by-step natural-language justification, a second LLM formalizes each step as a first-order implication, and an SMT check finds the invalid step, which becomes targeted feedback. 445 of 460 C programs (93.1%). — [LORIS, arXiv 2605.17914](https://arxiv.org/abs/2605.17914)
- [S] NeuroInv (Dec 2025) reports 99.5% on 150 Java programs using weakest-precondition reasoning with verifier feedback. — [NeuroInv, arXiv 2512.15816](https://arxiv.org/pdf/2512.15816v1)
- [V] SESpec (2025): symbolic execution computes strongest postconditions for loop-free segments; these and invariant *templates* constrain the LLM, which the authors say reduces hallucination and syntax errors. — [Yang et al., arXiv 2506.09550](https://arxiv.org/abs/2506.09550)
- [V] NeuroAbs (Aug 2026): for hardware property checking, an LLM selects signals and statements to abstract and proposes the abstract model over an AST representation; each abstraction is checked by SMT, and "if the abstraction is too coarse" CEGAR refines it. No numbers in the abstract. — [Yan et al., "NeuroAbs", arXiv 2608.17304](https://arxiv.org/abs/2608.17304)
- [V] PolyVer (FMCAD 2025): a system in several languages is modeled as a transition system whose update functions are C or Rust code; an LLM or syntax-guided synthesis proposes pre/post-condition contracts; language-specific verifiers (CBMC, Kani) check each contract against its code; the model checker (UCLID5) uses the contracts as abstractions; the tool alternates CEGAR and synthesis until the system property is proved or a real counterexample is found. — [Chen et al., "PolyVer", arXiv 2503.03207](https://arxiv.org/abs/2503.03207)
- [V] Agentic Model Checking (May 2026): "agents propose, solvers verify". LLM agents infer specifications from caller context in a restricted language that translates deterministically to assume/assert; each function is checked alone against stubs of its callees; counterexamples pass a validation pipeline (reachability, callee feasibility, dynamic replay), and modelling artifacts "drive refinement rather than being suppressed". The bounded model checker makes every soundness-relevant decision. — [Sun, Liu, Kroening, Xue, arXiv 2605.21434](https://arxiv.org/abs/2605.21434)
- [V] Event-B Agent (May 2026): an LLM agent builds an Event-B model from requirements and then refines and repairs it with feedback from formal verification, treating refinement and repair as mutually reinforcing. The abstract gives no numbers and does not say how gluing invariants are checked. — [Wang et al., arXiv 2605.17475](https://arxiv.org/abs/2605.17475)

### Inferences
- These numbers are for programs of tens of lines with one loop and a given target assertion. They do not transfer to a service handler with I/O. What transfers is the *shape* of the results: filtering beats raw sampling by about 30%, repair adds a few percent, and the checker's own failures are a visible share of the misses (10 of 71).
- Generate-and-filter should be the default; repair the exception. With repair at 16% against generation at 78%, re-asking with more context (a failing run, a template) is a better use of tokens than "fix this".
- LORIS's mechanism is prover-free in spirit: turn the LLM's justification into small checkable claims and find the first false one. Mental's analogue: have the LLM justify a summary case as a list of anchored steps and guards; the checker finds the first guard or anchor that does not match the full graph and returns exactly that.
- Disjunctions are where LLM invariants fail (44 of 71). Mental's summary behaviors *are* disjunctions (lists of guarded cases). The LLM should not be asked to invent the case split. The extractors already produce branch obligations; the split should come from them, with the LLM naming and merging cases. The existing "guards partition" check is the right guard here.
- SESpec and AutoSpec both say the same thing as Mental's "who decides what" table: the deterministic tool computes what it can (strongest postconditions, decomposition), and the LLM fills templates.
- LEMUR's cap k and its Unknown answer map directly: a bounded number of proposals per level pair, and a third outcome besides validated and refuted.
- NeuroAbs, PolyVer and Agentic Model Checking are prior art for "an LLM proposes the abstraction, a checker validates it, counterexamples refine it". PolyVer is the nearest in architecture: per-function contracts proposed by an LLM and checked against code become the abstraction that a system-level model checker runs. The draft's claim that Mental "would be the first to have an LLM propose a refinement level and a mechanical checker validate it per run" should be narrowed to what is still unclaimed: a *named ladder* of levels with vocabularies and state mappings, proposed from source code and checked by an interpreter rather than a solver.
- Agentic Model Checking's counterexample triage (is this failure real, or an artifact of the model?) is the same three-way classification the draft proposes for refinement failures.

### Gaps
- Most figures are from abstracts or one HTML read; NeuroInv is from a search summary. Several of these are preprints.
- No paper was found that measures LLM-proposed *predicate vocabularies* (names plus definitions) for predicate abstraction of software, or that reports stability of LLM proposals across commits.
- InvBench's headline accuracy figures were not extracted.

## 9. Translation validation applied to LLM output

### Takeaway
Where an LLM replaces the translator, existing validators are reused unchanged, and the measured validation rate is low. This is the most direct evidence for what Mental should expect when it validates LLM-proposed levels.

### Cited Findings
- [V] LLM-Vectorizer: an LLM rewrites scalar loops as vectorized code with test-based feedback; Alive2 then checks the result. Alive2 verified 38.2% of the vectorizations as correct on the TSVC benchmark; speedups of 1.1× to 9.4× over Intel, GCC and Clang compilers. — [Taneja et al., "LLM-Vectorizer", arXiv 2406.04693](https://arxiv.org/abs/2406.04693)
- [S] In that work, checksum testing judged one vectorization plausible while Alive2 found it inequivalent because of pointer aliasing; Alive2's verdicts are bounded because it unrolls loops. — [LLM-Vectorizer, arXiv 2406.04693](https://arxiv.org/pdf/2406.04693)
- [V] LLMLift: an LLM translates programs into four domain-specific languages and also generates the proofs of functional equivalence; the authors report more benchmarks transpiled and less time than symbolic lifting tools. — [Bhatia et al., "Verified Code Transpilation with LLMs", arXiv 2406.03003](https://arxiv.org/abs/2406.03003)
- [V] Wang and Xie: Alive2 runs first; when it cannot decide, a fine-tuned LLM predicts whether the transformation is unsound, and predicted-unsound cases are fuzzed for a counterexample. The LLM here helps the *validator*, and its verdict is only trusted when a counterexample confirms it. — [Wang & Xie, arXiv 2401.16797](https://arxiv.org/abs/2401.16797)
- [V] Trivet (Sep 2026): for LLVM translation validation, deterministic scaffolding generates the proof skeleton and discharges routine obligations; the LLM handles transformation-specific ones; the Lean kernel checks every verdict. It verifies or refutes 147 of 148 transformations, including 10 where Alive2 times out. Scaffolding enables 26 more proofs than an unscaffolded baseline and cuts mean proof time by 75.9% and cost by 88%. — [Liao et al., "Trivet"](https://cs.uwaterloo.ca/~cnsun/public/preprint/trivet/)

### Inferences
- 38.2% validated does not mean 61.8% wrong: the rest splits into wrong, timed out and unsupported. Mental should expect a large "not validated" bucket for LLM-proposed levels at first and must show it honestly, per level pair, with the reason.
- Tests passing and the validator disagreeing (the aliasing case) is the argument for symbolic and bounded-exhaustive modes over concrete scenarios alone when checking a level.
- Trivet's result is the strongest support in this sweep for Mental's division of labor: the deterministic scaffold made the LLM cheaper (88%) and more successful (26 more proofs). Give the LLM the skeleton (obligations, anchors, branch points) and ask it only for the judgment parts.
- Wang and Xie show the safe way to let an LLM help the checker: its opinion may direct effort (what to fuzz, which scenario to run) but only a concrete counterexample counts.

### Gaps
- LLMLift's proof-success rate and the checker it uses were not in the abstract.
- No work was found validating an LLM-written *abstraction of a distributed system* against its code by simulation or model checking, other than PolyVer and Agentic Model Checking in section 8.

## Corrections to the draft report

1. **CompCert's size.** The draft says "about 20 intermediate languages" and "about twenty intermediate languages". The sources say 8 intermediate languages (10 languages counting CompCert C and Asm) and 14 passes in 2009, 15 in the manual, 20 in the current pass table.
2. **Which CompCert passes are validated.** The draft says "some passes, such as register allocation, are not proved". The current pass table marks only register allocation as validated a posteriori, and its validator is itself proved sound. A *verified* validator gives the same guarantee as a proved pass; an unverified one (Necula, Alive2, and Mental) does not.
3. **"Predicates are computed rather than authored only in the model-checking family."** Too narrow. Abstract interpretation computes invariants; Daikon mines them from runs; Houdini filters candidates; IC3 learns lemmas; since 2023 LLMs propose them for a checker.
4. **"Maintenance across change is the weak point everywhere … the rest re-run from scratch."** Not so. CPAchecker stores precisions and reuses them across revisions (more than 4× faster on 1,119 revisions of 62 drivers); Goblint re-analyses incrementally by invalidating dependent results.
5. **"The level is chosen by choosing the domain, once per analysis."** True for a default IKOS run. Astrée's domains were extended whenever false alarms appeared; lazy abstraction and CPAchecker vary the precision by location and during the run.
6. **"No surveyed system proposes named levels … Mental would be the first to have an LLM propose a refinement level and a mechanical checker validate it."** NeuroAbs, PolyVer, Agentic Model Checking and Event-B Agent (2025–2026) have an LLM propose an abstraction, contract or refinement that a solver validates and counterexamples refine. The unclaimed part is narrower: a named ladder with vocabularies and state mappings, from source code, checked by an interpreter.
7. **"Nobody runs one end-to-end verifier."** Mostly right, with one nuance: Alive2 is used both after every pass and on arbitrary before/after pairs, so the pair being checked need not be adjacent.
8. **Missing systems.** The draft omits MLIR (the only precedent where levels are open-ended data, mixed in one program, with a declared legal set per conversion), CakeML (an explicit rule for when to add a level), Houdini, and all LLM-plus-checker work.
9. **Direction of soundness.** The draft treats CEGAR as a model for refining LLM predicates without noting that CEGAR's abstraction is sound by construction and only ever too coarse. An LLM-proposed abstraction can also be *unsound* (missing behavior), which CEGAR never has to detect.

## Recommendations for Mental

1. **Wrap every LLM stage as `Comp'`.** Output that fails its validator is an error or a quarantined record. A validator that cannot decide answers "not validated". (CompCert)
2. **Call the level check bounded translation validation and report five outcomes** per adjacent pair: validated within stated bounds, refuted with a run, timeout, unsupported construct, checker error. Always print the bounds. (Alive2)
3. **Check both directions and name them.** *Missing behavior*: a lower run whose projection the upper level does not allow (unsound summary; must fix). *Extra behavior*: an upper run that no lower run realizes (imprecise summary; refine). Compilers only need the first; CEGAR only meets the second; Mental has both.
4. **Declare each level as a namespace plus a legal set**, and implement the abstraction barrier as a full-conversion check; allow partial conversion for zoomed views, with explicit boundary adapters that fail loudly when missing. Build this before the interpreter. (MLIR)
5. **Add a level only when vocabulary disappears or appears.** Use this as the acceptance test for LLM-inserted levels and per-project domain ladders. (CakeML D0)
6. **Use the LLM as an oracle with a deterministic fallback.** If a proposed summary fails validation, fall back to the mechanically enumerated cases of the full graph. (CakeML)
7. **Make the LLM emit the relation with the level.** The abstraction function and step map are the "proof script" the validator consumes; do not try to infer them. (Pnueli; Necula's false alarms came from inferring)
8. **Refine predicates from failed replays.** When a summary run cannot be replayed on the full graph, the guard where the replay fails is the missing predicate; re-open only that behavior. (CEGAR, lazy abstraction)
9. **Store predicate sets as precisions, scoped by behavior, and reuse them across commits.** Start each rebuild from the stored set and re-validate. Key by port or function identity, not by statement position. (CPAchecker precision reuse)
10. **Over-propose and filter.** Ask the LLM for many candidate invariants and predicates; drop every one falsified in bounded exploration; keep the surviving set; show how many observations support each. Add Daikon-style mining from interpreter runs as a second source of candidates. (Houdini, Daikon)
11. **Prefer regenerate-with-evidence over repair; cap attempts.** Feed back the single failing guard or anchor, not "this is wrong". Cap proposals per pair. (Akhond et al.; LORIS; LEMUR)
12. **Do not let the LLM invent case splits.** Take the split from extracted branch obligations; let the LLM name and merge. Disjunctions are the main LLM failure class. (Loopy)
13. **Give the LLM a deterministic scaffold.** Obligations, anchors and templates first; judgment only in the holes. (Trivet, SESpec, AutoSpec)
14. **Default to the cheapest precision and refine on demand;** treat packs as domain-specific domains that remove false findings for one program family. (IKOS, Astrée)
15. **Cache level-pair results with dependency tracking** so that a commit invalidates only the pairs that depend on changed behaviors. (Goblint)
16. **Keep structural and semantic checks separate in the UI.** Anchors, coverage and partition checks say the level is well-formed, not that it agrees with the code. (MLIR's history)
17. **State that invariants hold "up to the bound".** Without widening or induction, the interpreter cannot claim more. (Astrée against Alive2)

## Open questions

- Which events are observable at each level, so that the pair check has a definite trace to compare? CompCert fixes this once (I/O events); Mental needs it per level.
- What false-alarm rate will users tolerate from the level check? Necula's 10% on some passes was acceptable for compiler testing; Alive2 chose zero and accepted missed bugs.
- Can the "missing behavior" direction be checked exhaustively at the summary level, using extracted obligations as the ground truth, so that only the "extra behavior" direction depends on bounded exploration?
- How stable are LLM-proposed predicate names and definitions across commits when seeded with the stored precision? No published measurement was found.
- Is behavior-scoped precision reuse enough when a refactor moves logic between functions? CPAchecker loses the precision on rename.
- Should Mental's model language get a small written semantics per level, as MLIR needed five years after launch, so that a failed pair check can be attributed to the model, the level, or the language?
- At what size does bounded exhaustive exploration of a level pair stop being affordable, and does the "holds is expensive, violated is cheap" asymmetry measured for CEGAR appear in the interpreter too?
- Would a tiny inductive check (an invariant holds initially and is preserved by every single step from any state satisfying it) be feasible in symbolic mode for some levels, giving unbounded results without a theorem prover, in the style of IC3 lemmas?
