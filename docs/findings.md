# Findings

Facts established so far, from two hand-made trials, the ladder-strategy experiments on rq, four research surveys and a few checks of outside facts. The [specification](specification.md) cites them by number.

Nothing here comes from running Mental: no tool exists yet. The trials were done by hand, by writing out what the tools should produce. Their working files are not kept in the repository.

## S. The hand-compiled model of report-jobs

**What was done.** The whole pipeline was simulated by hand on [`examples/report-jobs`](../examples/report-jobs/): every record of the model was written out in the planned format, two runs were written as traces, and a fix was applied and replayed.

**The subject.** About 150 lines of Python: a FastAPI service, two Celery worker replicas, a scheduled job, a command-line tool, Postgres, Redis and S3.

| # | Finding | Consequence for the design |
|---|---|---|
| **F-S1** | Frameworks own cases outside the handler. Request validation (a 422 answer) and unhandled exceptions (a 500 answer) happen in FastAPI, not in the handler's code. | These cases belong to the framework's pack. A handler's behavior covers only the handler. |
| **F-S2** | Instances need their own records. Replicas and per-instance config did not fit in the entity records. | The load phase writes `instances.jsonl`. |
| **F-S3** | Listing, per node, the predicates it *decides* was easy to write and made "this is not known yet" concrete. | Ordered reads are part of every behavior. |
| **F-S4** | Some cases exist only under concurrency. The "insert conflict" case cannot happen in a run with one activation; it becomes reachable only in search. | A case that looks dead in single runs must not be removed. |
| **F-S5** | Time conditions ("stuck for 15 minutes") work as choices made by the environment. No clock is needed in the configuration. | Time predicates are `env` choices. |
| **F-S6** | Config can make a port unreachable without deleting its branch. `WEBHOOK_URL` is unset, so the webhook is never called in this deployment, yet the branch is real. | Unreachable-by-config is a binding, recorded as such. |
| **F-S7** | A new check found a real bug: a state whose only exits need a message that may never exist (a *stranded* state). | The machine check includes stranded states. |
| **F-S8** | Framework rules leak into handler summaries. One path answers 202 because of the route decorator, not the handler body. Without the pack's summary in the prompt, the LLM would get it wrong. | Compile units always include pack summaries. |
| **F-S9** | Keeping anchors outside the records kept the model unchanged when lines moved. | Anchors live in their own file. |
| **F-S10** | Size and cost. Extraction gave 5 files, a call graph of 41 edges, 6 entry points and 2 state variables. The model had 23 entities, 26 ports, 18 wires (16 matched exactly, 1 by heuristic, 1 depending on an environment value), 13 instances, 15 predicates and 6 behaviors. The estimate was 15 LLM calls for the first build and 3 for the rebuild after a fix. | Cost per port is the number to measure first. Whether it scales is unknown. |
| **F-S11** | Four bugs were found (table below). The race was predicted by a static check and then found by search with bounds of 1 request, 2 replicas, 1 duplicated delivery and 1 preemption. The minimized witness had 23 steps. After the fix, replaying the stored schedule did not reproduce the violation, and a fresh search in the same bounds was clean. | These are the acceptance facts for the first compiler and interpreter. A replay alone does not verify a fix; a fresh search is needed. |
| **F-S12** | Three of the four bugs follow from mechanical facts alone (read and write sites, a pack rule, the replica count, a unique constraint). Only the stranded state used an LLM-written lifecycle, and most of that could be derived from the enum and the write sites. What the mechanical facts lack is readability: they give control-flow graphs where the compiled model gives a few named cases. | Supports keeping mechanical facts and LLM judgments apart, and is the main evidence for the "derived on demand" storage alternative. |
| **F-S13** | One link-time fact makes the race possible: with `task_acks_late = True` on Redis, the Celery pack makes delivery at-least-once, so one task can reach both workers. | Channel properties on wires must come from packs bound by config. |
| **F-S14** | The hand-compiled model missed a crash on every request, found later while recutting the example into moves. With SQLAlchemy's default `expire_on_commit=True`, a commit expires every loaded object. `api.py:33` and `tasks.py:75` then read `report.id` after their `with Session()` block has closed the session, and that raises `DetachedInstanceError`: every `POST /reports` stored a `PENDING` row and answered 500 without queueing it, and `requeue_stuck` crashed before re-queueing anything. The same default turns each attribute read after a commit into a hidden `SELECT` (`tasks.py:39`, `tasks.py:53`). Checked on SQLite with the pinned SQLAlchemy 2.0.36 in a stand-alone script; the app itself was not run. The example now sets `expire_on_commit=False` in `db.py`, which keeps every line number and the four bugs below. | The SQLAlchemy pack must model session configuration: expiry on commit makes later attribute reads into reads of the store, and an expired object read after its session closes raises. A model that treats ORM attributes as local variables misses both. |

**The four bugs.**

| Bug | What happens |
|---|---|
| Duplicate claim | Both workers read `PENDING` before either writes `RUNNING`; both build and upload the report. |
| Lost update | `requeue_stuck` loads a `RUNNING` row and writes `PENDING` without re-checking; if the worker marked it `DONE` in between, `DONE` is overwritten. |
| Unhandled conflict | Two requests with the same idempotency key both pass the lookup; the second insert violates the unique constraint and that request gets a 500. |
| Stranded row | The API commits a `PENDING` row and then fails to queue the task (the queue is down). Nothing ever picks the row up. |

## Z. One run at seven levels

**What was done.** The duplicate-claim race was written by hand at seven levels, with a link from every step to the step it refines at the level above, and a small checker for those links. A throwaway viewer animated between the levels.

| Level | Steps | New at this level | Passed through unchanged |
|---|---|---|---|
| Business | 4 | 4 | 0 |
| System | 6 | 6 | 0 |
| Services | 21 | 21 | 0 |
| Components | 26 | 26 | 0 |
| Mechanisms | 26 | 14 | 12 |
| Statements | 30 | 25 | 5 |
| Postgres internals (from the database's own model) | 34 | 9 | 25 |

| # | Finding | Consequence for the design |
|---|---|---|
| **F-Z1** | Zoom works as a mapping by step identity, not by position. At the services level the steps of "deliver the report" and "deliver it again" interleave, while the level above shows them one after the other. | Moving between levels follows the links between steps, never row numbers. |
| **F-Z2** | A level adds detail only where its vocabulary applies. Mechanisms change 14 of 26 steps; the Postgres level changes 9 of 34. A checker confirmed the links were complete: every step is refined or passed through. | "Unchanged at this level" is a first-class notion, and coverage of the step map is a check. |
| **F-Z3** | Entities split as well as steps: Postgres into the `reports` row and `orders`; the row gives up a *status lock*; the lock is implemented by row versions inside Postgres. One parent link per entity was enough. | An entity has a parent per level. A mechanism carved out of a column needs no new record kind. |
| **F-Z4** | Each problem has a level where it can be named. Business and system show only symptoms (delivered twice, stored twice). The duplicate delivery is named at services; the illegal write at components; "two holders" at mechanisms. Whether the fix (`… AND status = 'PENDING'`) works is decided only inside Postgres, by how READ COMMITTED re-checks a row. | Upper levels carry "cause further down" markers. The open question on isolation levels is answered in the database pack's own lower level. |
| **F-Z5** | The database's internal level has meaning only for database steps; everything else passes through. It behaves like zooming into one entity. | A pack's own levels attach as a branch, not as one more rung for the whole system. |
| **F-Z6** | Upper-level data is aggregation. The business step carries "deliveries: 2", which is a count of lower steps and a field of no single message. | A level's vocabulary needs derived attributes. |
| **F-Z7** | One total order of steps per level is a simplification. Concurrent steps in two workers have no real order between them. | Traces are partial orders; a view should let the order of independent steps be flipped. |
| **F-Z8** | In the trial the links between levels were written per run. They belong in the model: each node names the upper step it implements. | Any run can then be shown at any level with no extra data. |
| **F-Z9** | The throwaway viewer is not a design for the product. It used a sequence diagram, switched the whole view to one level at a time, and showed one zoom axis and one total order. | What the viewer looks like is a separate, open study. |

**Not tested:** producing the levels automatically; zooming in space and time at once; the fixed version of the code; a project whose own domain has several levels.

## R. Research

Three surveys of published work. Full reports: [static analysis and LLM system models](research/static-analysis-llm-system-models/report.md), [model interpreter semantics](research/model-interpreter-semantics/report.md), [abstraction levels](research/abstraction-levels/report.md). The figures come from published studies, mostly on LLMs of 2023 to 2025.

| # | Finding | Consequence for the design |
|---|---|---|
| **F-R1** | Static call graphs are more complete than LLM-made ones: about 85% against 60% on Python. | Structure comes from extractors. |
| **F-R2** | Specifications written by an LLM and fed to a static engine double what the engine finds (27 to 55 known vulnerabilities in one study). | The LLM writes summaries and names that mechanical tools then use. |
| **F-R3** | When an LLM decides which reports or branches to drop, 27.5 to 45% of confirmed bugs are lost. When the LLM only adds context to a sound analyzer, none are. | The LLM never removes a branch or decides feasibility. |
| **F-R4** | Every field that relates several levels of description does the same three things: gives each level its own vocabulary and steps, records how lower state maps to upper state, and records which lower steps realize each upper step. Agreement is established per *pair* of adjacent levels, never end to end. Model checkers establish it by exploring states, with no prover. | The `level` record and the pair check. |
| **F-R5** | The precedents for running a model agree on a small design: one step relation over configurations (as in the P language), all nondeterminism in a recorded scheduler outside the rules, and concrete, symbolic and exhaustive runs as strategies over the same two functions. Atomicity must be computed from what steps read and write; a wrong grain of atomicity is the best-documented failure of hand-written and LLM-written models. | The interpreter's design. |
| **F-R6** | No production tool for Python, TypeScript or Go produces function summaries split by path condition; none infers state machines from undeclared status fields; none links services across repositories. | These parts must be built; they cannot be bought. |
| **F-R7** | LLMs asked to write an upper level tend to pass checks by making that level permissive. Countermeasures: require every case to be witnessed by a lower run, mutate lower runs and require some mutants to fail, and reject levels that restate the level below. | Planned guards for the level checks. |
| **F-R8** | Other projects already have an LLM propose an abstraction that a tool checks. None has an LLM propose a named ladder of several levels, each with vocabulary, state mapping and behavior, derived from source and checked by an interpreter. | This is where Mental is new. |

## L. Ladder strategies on rq

**What was done.** Experiments L2 to L5 of the [ladder strategies](ladder-strategies.md#8-experiments), on 2026-11-17, first on rq (F-L1 to F-L6), then on report-jobs (F-L7 to F-L11), in the research harness of the [multi-level experiments](research/multi-level-models/experiments/README.md). On rq: 2.12, with 2.0 and 3.0 for stability, 2,097 explored runs, 554 anomalous. On report-jobs: its real code under a new harness, 115 runs, 24 anomalous, and a copy that only moves lines for stability. Each experiment changes one option of the strategy `closing-rules` and keeps the rest as in the first experiment, whose numbers the code reproduces exactly. LLM calls: on rq six naming samples and 18 stand-in reader calls ($1.65); on report-jobs twelve naming samples ($0.69).

| # | Finding | Consequence for the design |
|---|---|---|
| **F-L1** | Closing a move at the end of an optimistic transaction gives the same moves as closing at every write: no on-chain write falls inside an open transaction except its commit. | The `atomic-group` rule is untested until a subject writes inside a transaction (report-jobs). |
| **F-L2** | Joining consecutive writes to the same key into one move (`write-run`) cut moves per run from 7.3 to 5.0 and kept every cause at its level and every explaining cut at most 6 lines. Stability against rq 2.0 rose from 0.52 to 0.61. The stand-in reader answered all 18 developer questions from 7 to 11 lines, against 14 of 18 from 9 to 15. It is coarser than the hand grouping. | `write-run` is the proposed working default for moves, pending report-jobs. |
| **F-L3** | Giving the namer each move's head effect cut name-truth failures from 20 to 6 of 174 move names, and removed *record worker heartbeat*, but did not raise agreement (22% identical either way). Activation names agreed less (21% to 6%), because they followed the head move instead of the call. | Use the head for move names as a truth aid, not for stability; names are generated once and stored. |
| **F-L4** | A name-truth check by nouns and written key families flagged 20 of 174 earlier move names, of which 15 were right: words naming the step's own call, and lists that hold what the name mentions. | The check needs the glossary's knowledge of what a thing contains, and must exempt the call's own words. |
| **F-L5** | Filing each goal under one outcome hides, in 8% of outcomes, a change made to that outcome's own job. Listing a goal under every job it changes costs nothing in where symptoms and causes show. | Outcomes are object-centric. |
| **F-L6** | Of three merge tests, only "merge when four in five upper steps have one lower step" merges the levels that restate a neighbour (stage and exchange into goal) and keeps every level that names causes. The band and the step-length overlap test would both merge move into effect, losing the level that names 285 of 554 causes, because most moves are one effect long. | Merge test `single-child`; step length alone does not separate levels. |
| **F-L7** | Report-jobs' real code, run one database read, commit, upload and message at a time, gives 115 runs at two preemptions. 24 are anomalous, and they are three of its four known bugs: a double claim that uploads twice, `requeue_stuck` setting a finished report back to PENDING, and a 500 on a duplicate idempotency key. The fourth, a PENDING row nothing picks up, happens without concurrency, so the sequential-run oracle cannot see it. | A harness for a second subject exists; sequential bugs need another oracle (the machine check). |
| **F-L8** | On report-jobs all three move rules give identical moves. The only write inside an open transaction is the upload, which ends the activation, and no two consecutive writes go to the same key. | `write-run` is the default (it won on rq, ties here); `atomic-group` and `prefer` changed nothing on two subjects. |
| **F-L9** | Moves identified by their closing call site (`generate_report:32`) survive a change that only moves lines 5% of the time. Identified by the function and the order of the closing site in it, all 11 classes survive and none collide. Without the write set, the same identity scores 0.875 and 0.50 on rq's versions, as the function-only identity does. | Move identity: call, closing function, order of the closing site. Answers the specification's open question for report-jobs. |
| **F-L10** | On report-jobs, giving the namer each move's head raised exact agreement on move names from 9% to 21%, without loss of truth. Activations did not gain, and two Opus samples let the SQL word "insert" into 5 names. | `head` for move names, with the barrier check; `children` for activations and goals. |
| **F-L11** | On report-jobs, as on rq, only the `single-child` merge test merges exactly stage and exchange into goal and keeps every level that names an anomaly. The other two tests would merge activation into move. A stage signature that kept subject ids had made 8 runs look named at stage, because report-jobs' ids depend on creation order. | `single-child` decided on two subjects; level signatures never include ids. |

## U. Unresolved references and dependencies

A fourth survey, made on 2026-11-14 in two rounds: a broad survey, then a second round that re-read the primary source of every claim the design leans on. Report: [unresolved references](research/unresolved-references/report.md). The verified notes are [`verified_*.md`](research/unresolved-references/notes/); each claim there carries a quote and a link. The [resolution specification](resolution.md) cites these findings. Figures for LLMs come from the models named, mostly of 2024 and 2025.

| # | Finding | Consequence for the design |
|---|---|---|
| **F-U1** | Projects often do not build unattended. Of 7,264 GitHub Java projects with a build file, 38% failed their default build in 2016, and dependency problems were 39% of the failures ([Sulír and Porubän](https://arxiv.org/abs/1712.01024)). A 2020 replication found 59% failing ([registered report](https://arxiv.org/abs/2408.11544)); its 2026 results put build success at 30 to 44% per JDK, with about 32% of projects failing under every JDK. Only 38% of a project's history still compiles (Tufano et al.). No comparable study exists for Python, JavaScript, Go or Rust repositories. | The extractor must not need a build. |
| **F-U2** | Lockfiles are committed unevenly. Among 4,859 popular GitHub projects: Go 99.7%, Pipenv 86.2%, Poetry 83.8%, Cargo 70.9%, npm 53%, pnpm 36%, Gradle 0.9% ([Gamage et al.](https://arxiv.org/html/2505.04834v3)). Where a lockfile is the input, dependency tools are exact on name and version ([2,414 repositories](https://arxiv.org/html/2511.20313v2)); without one, Java recall was 37 to 55% against 98% for a tool using the build tool's own resolution, and Python version accuracy 22 to 31% ([10,000 repositories](https://arxiv.org/html/2607.04614)). | Committed pins first; the rate of unpinned packages depends on the ecosystem. |
| **F-U3** | Static call graphs miss real calls even with everything available. Java: median recall 0.884 of reachable methods on 31 programs ([Sui et al.](https://ecs.wgtn.ac.nz/foswiki/pub/Main/JensDietrich/recall.pdf)). Python: PyCG has 99.2% precision and 69.9% recall on five projects ([Salis et al.](https://arxiv.org/pdf/2103.00587)). JavaScript: 75.9% recall, rising to 88.1% with approximate interpretation ([Jelly](https://cs.au.dk/~amoeller/papers/approx/paper.pdf)). | "Everything resolved" does not mean "everything found". Unresolved references are a property of static analysis, not of a missing environment. |
| **F-U4** | CodeQL's Python analysis extracts no dependencies since CLI 2.16.0 (January 2024) and not even the standard library since 2.19.2 (October 2024), "relying instead on models of the standard library"; GitHub states the effect on alerts "should be minimal" ([CLI changelog](https://github.com/github/codeql-cli-binaries/blob/main/CHANGELOG.md)). Library code is referred to by import path through [API graphs](https://codeql.github.com/docs/codeql-language-guides/using-api-graphs-in-python/). | An external reference needs no library source: an access path from the import is an identity. |
| **F-U5** | CodeQL is the only tool found that measures what it failed to resolve and applies a threshold. Two metrics, the share of calls with a known target and of expressions with a known type, raise a warning below 85% for Java and C# (50% and 20% for Rust), and the scan still succeeds ([query](https://github.com/github/codeql/blob/main/java/ql/src/Telemetry/DatabaseQualityDiagnostics.ql)). The threshold started at 95% and was lowered, and C# and Rust removed call kinds from the count after false alarms ([changelog](https://github.com/github/codeql/blob/main/java/ql/src/CHANGELOG.md)). C and C++ publish the metric with no threshold. Without a build, CodeQL for Java guesses dependencies from package names and does not analyse generated code ([docs](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages)). No tool was found that fails on such a rate. | A rate is worth reporting and is a poor gate. Guessing dependencies is the degraded path not to copy. |
| **F-U6** | Tools that work without a build mark the hole and carry on. Joern writes placeholders into the name, such as `<unresolvedNamespace>.foo:<unresolvedSignature>(1)` ([source](https://github.com/joernio/joern/blob/master/joern-cli/frontends/x2cpg/src/main/scala/io/joern/x2cpg/Defines.scala)); scip-python makes a file-local symbol documented "unable to resolve module" ([source](https://github.com/sourcegraph/scip-python/blob/scip/packages/pyright-scip/src/treeVisitor.ts)); Kythe has a `lookup` node for "a structured name whose resolution cannot be completed" ([schema](https://kythe.io/docs/schema/)); go/packages attaches errors per package and sets `IllTyped` ([source](https://github.com/golang/tools/blob/master/go/packages/packages.go)). mypy and Pyright can report the share of untyped expressions or symbols per file. Sourcegraph falls back from precise to search-based navigation, which matches by name. Tools for coding agents (tree-sitter graphs, embeddings) match by name and publish no resolution rate. | Mental's `Unresolved(reason)` is in line with practice. Reporting the rate, and failing where it matters, is new. |
| **F-U7** | A library can be left unanalysed soundly under the **separate compilation assumption**: library code compiles without the application, so it can reach application code only through what the application passes to it or derives from it. With one summary node for the whole library, application call graphs were sound against dynamic ones except for one edge, with a median of 41 extra edges against a whole-program analysis ([Ali and Lhoták 2012](https://plg.uwaterloo.ca/~olhotak/pubs/ecoop12.pdf), [2013](https://plg.uwaterloo.ca/~olhotak/pubs/ecoop13.pdf)). | Callbacks and overrides ("escapes") are the complete list of ways outside code calls in. |
| **F-U8** | Framework wiring is recovered by declarative models, not deeper analysis. On Java enterprise applications a framework-aware analysis reached 58% of application code against 14% for the plain one (JackEE, PLDI 2020). | Packs and slots are the largest lever for framework code. |
| **F-U9** | Partial-program type inference is good and not exact: 91.2% correct and 2.7% wrong types with one class visible (PPA, 2008). | Inferred types are candidates, not facts. |
| **F-U10** | Python lock formats: only `pylock.toml` is specified (PEP 751, Final since March 2025); uv, pip and PDM write it, pip and uv read it. `uv.lock`, `poetry.lock` and `pdm.lock` have no published schema, and uv states "the lockfile format is not guaranteed to be stable" ([uv](https://github.com/astral-sh/uv/blob/main/docs/reference/internals/metadata.md)). All four record the resolved commit of a git dependency ([spec](https://github.com/pypa/packaging.python.org/blob/main/source/specifications/pylock-toml.rst)). A requirements file may hold ranges, includes and options and is "only intended for consumption by pip". | Read `pylock.toml` by the spec and the others by schema version, failing on an unknown one. |
| **F-U11** | An installed Python environment is readable as data. Only `METADATA` is guaranteed per distribution; `RECORD` and `direct_url.json` (which holds the commit of a git install) are optional; `top_level.txt` is in no standard. The standard library maps import names to distributions from `top_level.txt`, falling back to `RECORD` paths. uv and PDM put the environment in `.venv` in the project; Poetry and pipenv keep it elsewhere ([uv](https://github.com/astral-sh/uv/blob/main/docs/concepts/projects/layout.md)). Editable installs through import hooks "are not usable by Pyright and other static analysis tools". typeshed lists each standard-library module with its Python versions in [`stdlib/VERSIONS`](https://github.com/python/typeshed/blob/main/stdlib/VERSIONS). | Rung 2 of resolution, and the source of the standard-library table. |
| **F-U12** | Python resolvers execute code to resolve: pip and uv build source distributions with the project's build backend when metadata is not otherwise available, and the flags that prevent it (`--only-binary :all:`, uv's `--no-build`) do not cover local, git or editable sources ([pip](https://github.com/pypa/pip/blob/main/docs/html/cli/pip_install.rst)). Automatic lockfile generation succeeded for only 19% of Python repositories in one study, against 96% for Rust ([study](https://arxiv.org/html/2511.20313v2)). | `mentalc` does not generate lockfiles or environments. |
| **F-U13** | Type information for Python libraries is patchy. In 2024, 114 of the 2,000 most downloaded PyPI packages had typeshed stubs ([forum post](https://discuss.python.org/t/prevalence-staleness-of-stubs-packages-in-pypi/70457)). Of 11,021 libraries, 83% have at least one annotation, and coverage "remains limited and uneven" ([Asare and Nadi](https://www.ericasare.org/papers/MSR26.pdf)). No measured share of packages shipping `py.typed` was found. | Reading library surface helps some packages only; it cannot be required. |
| **F-U14** | Build tools execute repository-controlled code even for read-only questions. Gradle "first runs any init scripts, then evaluates the settings file" on every invocation ([lifecycle](https://docs.gradle.org/current/userguide/build_lifecycle.html)). Maven loads the extensions named in `.mvn/extensions.xml` ([docs](https://maven.apache.org/configure.html)). Yarn runs the binary named by `yarnPath` "for any command run within the directory" ([docs](https://yarnpkg.com/configuration/yarnrc)). A `go.mod` can make the `go` command download and run another toolchain ([docs](https://go.dev/doc/toolchain)). npm 12 (July 2026) blocks dependency install scripts by default, while the root project's scripts and a new root hook still run ([changelog](https://github.blog/changelog/2026-07-08-npm-install-time-security-and-gat-bypass2fa-deprecation/)); the allow-lists of npm, pnpm and Composer live in the repository. | Asking a build tool is executing the repository. An allow-list in the repository is not the user's trust. |
| **F-U15** | Git's manual: "it is not safe to run Git commands in a `.git` directory (or the working tree that surrounds it) when that `.git` directory itself comes from an untrusted source" ([git(1)](https://git-scm.com/docs/git)). | `mentalc` reads `.gitmodules` as text and does not run git. |
| **F-U16** | `docker compose config` is documented to "parse, resolve and render" only, and by default it substitutes variables from the calling shell; `--no-interpolate` turns that off ([docs](https://docs.docker.com/reference/cli/docker/compose/config/)). | Left as is, the model depends on the developer's shell and can absorb its secrets. |
| **F-U17** | A coding agent's permission prompt does not cover what a tool starts. In Claude Code "a Bash rule matches the command text Claude writes" ([permissions](https://code.claude.com/docs/en/permissions)); the sandbox covers a shell command's child processes only when it is on; local MCP servers "run with your full access" ([sandboxing](https://code.claude.com/docs/en/sandboxing)); headless sessions show no trust dialog. | `mentalc` needs its own default-deny. When a command must run, the agent runs it, so the prompt sees it. |
| **F-U18** | IDEs gate project import behind trust because import runs the build: in IntelliJ's Safe Mode "no build scripts are executed and no dependencies are resolved" ([docs](https://www.jetbrains.com/help/idea/project-security.html)); VS Code's Restricted Mode disables agents, terminals and tasks ([docs](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust)). Until Gradle 9.7 with IntelliJ IDEA 2026.2, one failing build script left the IDE with no model at all ([Gradle](https://blog.gradle.org/resilient-sync)). | Precision by running the build needs a human. A partial result with named holes is recent even for IDEs. |
| **F-U19** | Sliding versions and git sources. Maven has no lockfile and Maven 4 is not released ([history](https://maven.apache.org/docs/history.html)). Gradle's lockfile holds versions with no edges and no hashes, and dynamic and changing versions are re-checked every 24 hours. The lockfiles of npm, pnpm, Yarn, Bun, Cargo and Python, and Go's pseudo-versions, all record the commit of a git dependency. A submodule's commit is in the superproject's tree; a subtree's only in commit messages. Image tags are mutable and a digest is the only pin. GitHub Actions has a lockfile, generally available since 2026-10-28 ([changelog](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/)); 6% of 382 workflows pinned an action by commit ([study](https://arxiv.org/abs/2507.18062)). | A dependency from GitHub is as exact as one from a registry wherever a lockfile exists. Sliding versions are unknowable only where nothing records them. |
| **F-U20** | Identity formats. The package URL is a standard (ECMA-427) with types for registries and for `git`, and is embedded in CycloneDX, SPDX and lockfile tools ([spec](https://github.com/package-url/purl-spec)). SCIP names an external symbol by manager, package, version and a descriptor path; scip-python names the standard library as the synthetic package `python-stdlib`. | External symbols use package URLs. |
| **F-U21** | LLMs infer local types well and unfamiliar ones less well. On a micro-benchmark of 860 annotations gpt-4o matched 93.7% against 65.5% for the best static tool ([Venkatesh et al.](https://arxiv.org/html/2410.00603v2)). On user-defined types not seen in training, the best systems reach 64 to 68% at the first guess ([TIGER](https://arxiv.org/abs/2407.02095)). On whole repositories gpt-4o's annotations produce 366 type-check errors per repository against 142 for the human ones ([TypyBench](https://arxiv.org/abs/2507.22086)). | Good enough to propose a type, not to assert one. |
| **F-U22** | LLMs build call graphs worse than static tools: the best LLM is complete on 76 of 126 cases against 107 for PyCG, and on flow-sensitive call sites it matches 28.5% against 91.3% for a static tool ([same study](https://arxiv.org/html/2410.00603v2)). This is the source of F-R1. | Structure stays with the extractor. |
| **F-U23** | Giving an LLM only the calls a static tool could not resolve works, and its error rate is unmeasured. SemTaint cut 94,909 unresolved calls to 5,195 sent to the LLM and found 106 of 162 vulnerabilities the static tool missed ([paper](https://arxiv.org/abs/2601.10865)). Facet restricts the LLM to candidates found symbolically and checks each choice: spurious edges fell from 6,872 to 1,156 with recall unchanged. No design publishes how often its checker accepts a wrong answer. | The pattern for experiment E2-B. Mental has to measure false acceptances itself. |
| **F-U24** | An LLM that filters static findings discards true ones: 6 to 46% of real bugs across models and techniques in an industrial study of 433 alarms ([paper](https://arxiv.org/abs/2601.18844)). An LLM that writes specifications for a static engine doubles detections, 27 to 55 of 120, while 85% of what is reported stays false ([IRIS](https://arxiv.org/abs/2405.17238)). Confirms F-R2 and F-R3 with newer models. | The LLM never dismisses a gap. |
| **F-U25** | Agents set up build environments unreliably and slowly: from 6.7% of hard Python repositories ([EnvBench](https://arxiv.org/abs/2503.14443)) to 86% of 420 on another benchmark at 29 minutes each ([Repo2Run](https://arxiv.org/abs/2502.13681)); 33 of 50 projects at 74 minutes each ([ExecutionAgent](https://arxiv.org/abs/2412.10133)). The benchmarks define success differently and cannot be compared. | Building an environment is not a default step of a build. |
